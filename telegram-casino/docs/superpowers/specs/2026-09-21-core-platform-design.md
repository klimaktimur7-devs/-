## Контекст

Полное ТЗ описывает Telegram Mini App-казино: единый баланс, 6 инхаус-игр (PvP,
Краш, Лимбо, Гифт Плинко, Болл Ескейп, Апгрейд), 800 слотов + live-модуль через
внешнего агрегатора, магазин NFT Gifts (Fragment), стейкинг, реферальная
программа и отдельная админ-панель. Это слишком большой объём для одного
спека/плана, поэтому работа разбита на подпроекты:

1. **Ядро платформы** (этот документ) — авторизация, баланс/леджер, навигация,
   первый способ депозита.
2. Депозит: TON Connect / Gram, Telegram Gifts, @CryptoBot (расширение метода 1).
3. Игры (по одной: PvP, Краш, Лимбо, Гифт Плинко, Болл Ескейп, Апгрейд).
4. Магазин NFT Gifts + вывод.
5. Стейкинг.
6. Реферальная система.
7. Лидерборд.
8. Интеграция агрегатора слотов/live-казино.
9. Админ-панель.

Проект оформляется под лицензию на организацию азартных игр (подтверждено
заказчиком) — часть требований ниже (раздел «Compliance») добавлена поверх
исходного ТЗ именно по этой причине и должна сохраняться во всех последующих
подпроектах.

## Что входит в этот подпроект

Единый Telegram Mini App-каркас: вход по Telegram ID, единый внутренний баланс,
таббар-навигация из 5 вкладок (рабочая — только «Профиль», остальные —
заглушки «Скоро»), и депозит в Telegram Stars как первый способ оплаты.
Экраны самих игр, магазина, стейкинга, рефералки и лидерборда — вне рамок
этого подпроекта.

## A. Структура репозитория

## B. Авторизация

Фронтенд получает `initData` через Telegram WebApp SDK при старте мини-аппа и
передаёт его на бэкенд при каждом запросе (или один раз для обмена на сессию).
Бэкенд валидирует HMAC-SHA256 подпись `initData` секретом бота (это
единственный способ криптографически подтвердить, что запрос от Telegram, а
не подделан) → находит или создаёт пользователя по `telegram_id` → выдаёт JWT
для последующих вызовов API. Без пароля и формы регистрации, как в ТЗ.

Невалидная подпись или истёкший `auth_date` → 401, запрос отклоняется.

## C. Баланс и леджер

Единая внутренняя валюта (рабочее название — **Gram**, как в ТЗ). Пополнения в
Stars/TON/крипте/подарках конвертируются в неё по курсу, зафиксированному в
момент операции (курс сохраняется в записи леджера для аудита, а не
пересчитывается заново).

Баланс не хранится как отдельно изменяемое число — он выводится из
неизменяемых записей леджера (double-entry: каждая операция — минимум две
проводки, дебет/кредит, сумма которых по счёту равна нулю). Обязательно для
предсказуемой сверки и последующего AML-аудита, тем более для проекта под
лицензией.

Таблицы (первое приближение, детали — на этапе плана):
- `users` (telegram_id, username, consent_accepted_at, language_code, …)
- `ledger_entries` (user_id, amount, currency=GRAM, type: deposit/withdrawal/bet/win/…,
  external_ref, created_at)
- `deposit_intents` (telegram_payment_charge_id как идемпотентный ключ, статус,
  сумма в исходной валюте, курс на момент операции)

## D. Депозит v1 — Telegram Stars

1. Фронтенд запрашивает у бэкенда инвойс на сумму N Stars.
2. Бэкенд создаёт инвойс через Telegram Bot API (`createInvoiceLink`,
   `currency=XTR`), возвращает ссылку фронтенду.
3. Telegram открывает системный лист оплаты (это UI самого Telegram, не
   кастомизируется).
4. После оплаты бот получает `successful_payment` через webhook.
5. Бэкенд по `telegram_payment_charge_id` (идемпотентный ключ) зачисляет Gram
   через леджер-запись. Повторный вебхук с тем же `charge_id` не должен
   задваивать баланс — обязательный тест.

TON Connect, Telegram Gifts, @CryptoBot — в подпроекте 2, интерфейс депозита
проектируется так, чтобы добавление метода не требовало переделки существующего
флоу (единая внутренняя модель `deposit_intent` уже не привязана к конкретному
методу).

## E. Навигация и экраны

Таббар внизу экрана: ПвП / Соло / Магазин / Награды / Профиль (иконки и подписи
— по ТЗ, раздел 9). В этом подпроекте:

- **Профиль** — рабочий экран: аватар и имя из Telegram, баланс, кнопка
  «Пополнить», статистика-заглушка (0 игр), пустой инвентарь.
- **ПвП / Соло / Магазин / Награды** — заглушки «Скоро».
- Кнопка «Пополнить» в шапке — видна на любом экране, открывает модалку с
  выбором метода (в v1 — только Stars).

Цвета, кнопки, анимации — по дизайн-системе ТЗ (раздел 10.1–10.2): тёмная
тема, фон `#0D0D0D`/`#111118`, акцент `#7C3AED → #A855F7`, кнопки с
градиентом/тенью/haptic feedback. Экраны и графика самих игр (колесо PvP,
ракета Краша и т.п.) — не в этом подпроекте; референсы из ТЗ (скриншоты
Darilo/Rolls/Balls) — это чужие продукты, используются только как ориентир по
паттернам UX, не копируются визуально.

## F. Compliance-надстройки (сверх исходного ТЗ)

Добавлено, так как проект оформляется под лицензию:

- Экран согласия 18+ и с правилами платформы при первом входе — блокирует
  доступ до принятия, согласие сохраняется с таймстампом и версией текста
  правил.
- Поле «предполагаемая юрисдикция» — пока грубая эвристика (`language_code` из
  Telegram), реальный гео-блок запрещённых стран — отдельная задача, когда
  определится список юрисдикций (не в этом подпроекте).
- Kill-switch — env-флаг, отключающий приём депозитов на всей платформе без
  деплоя (на случай регуляторных проблем).
- Леджер сам по себе закрывает базовую AML-трассируемость: любая операция с
  балансом воспроизводима и неизменяема.

## G. Тестирование

NestJS e2e:
- Валидация `initData` — успех с верной подписью, отказ с неверной/просроченной.
- Флоу депозита Stars с замоканным вебхуком: создание инвойса → зачисление →
  баланс обновился.
- Идемпотентность: повторная отправка того же `successful_payment` не меняет
  баланс повторно.
- Инвариант леджера: сумма проводок по пользователю равна отображаемому
  балансу.
