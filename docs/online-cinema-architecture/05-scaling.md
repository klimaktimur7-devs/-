# 5. Стратегия масштабирования

## 5.1. Расчёт ёмкости

Масштабирование начинается с явного расчёта нагрузки на каждый компонент. Без него решения о числе шардов, узлов и партиций принимались бы наугад. Ниже приведена модель, из которой выведены все цифры раздела. Она реализована скриптом, который пересчитывается при каждом изменении прогноза роста.

```python
# capacity_model.py — базовая модель ёмкости платформы.
from dataclasses import dataclass

@dataclass
class Inputs:
    mau: int = 50_000_000
    dau_ratio: float = 0.36
    watch_hours_per_dau: float = 1.2
    avg_bitrate_mbps: float = 3.5
    peak_concurrency_ratio: float = 0.22      # доля DAU, смотрящих в пиковый час
    api_calls_per_dau: int = 150
    api_peak_factor: float = 3.0
    heartbeat_interval_s: int = 60
    telemetry_batch_interval_s: int = 30
    events_per_batch: int = 10
    segment_seconds: float = 4.0

def model(i: Inputs) -> dict:
    dau = i.mau * i.dau_ratio
    peak_streams = dau * i.peak_concurrency_ratio
    peak_tbps = peak_streams * i.avg_bitrate_mbps / 1_000_000
    gb_per_hour = i.avg_bitrate_mbps / 8 * 3600 / 1000
    monthly_pb = dau * i.watch_hours_per_dau * 30 * gb_per_hour / 1_000_000
    api_avg_rps = dau * i.api_calls_per_dau / 86_400
    return {
        "dau": dau,
        "peak_streams": peak_streams,
        "peak_egress_tbps": round(peak_tbps, 1),
        "monthly_traffic_pb": round(monthly_pb),
        "api_peak_rps": round(api_avg_rps * i.api_peak_factor),
        "heartbeat_peak_rps": round(peak_streams / i.heartbeat_interval_s),
        "telemetry_batches_rps": round(peak_streams / i.telemetry_batch_interval_s),
        "telemetry_events_per_s": round(peak_streams / i.telemetry_batch_interval_s * i.events_per_batch),
        "segment_rps": round(peak_streams * 2 / i.segment_seconds),   # видео + аудио
    }

if __name__ == "__main__":
    for k, v in model(Inputs()).items():
        print(f"{k:>24}: {v:,}")
```

Результат расчёта:

| Показатель | Значение | Что масштабируется |
|------------|----------|--------------------|
| DAU | 18 000 000 | — |
| Пиковые одновременные потоки | ~3 960 000 (≈4 млн) | CDN, Concurrency, Playback |
| Пиковый исходящий трафик | ~13,9 Тбит/с | CDN и appliance |
| Трафик в месяц | ~1 020 ПБ | Стоимость CDN |
| Пиковый RPS «обычного» API | ~94 000 | Шлюз, BFF, доменные сервисы |
| Пиковый RPS heartbeat | ~66 000 | Playback, Progress, Cassandra |
| Пиковый RPS пакетов телеметрии | ~132 000 | Telemetry Ingest |
| Пиковое число событий телеметрии | ~1 320 000 в секунду | Kafka, ClickHouse |
| Пиковый RPS сегментов | ~1 980 000 | Edge-кэши |

Суммарный пик API без сегментов составляет около 300 тысяч RPS. Мы проектируем систему с запасом ×2 (600 тысяч RPS), потому что премьеры популярных сериалов создают кратковременные всплески в 3–5 раз выше обычного пика в первые минуты после выхода.

## 5.2. Горизонтальное масштабирование stateless-сервисов

Все сервисы плоскости управления, кроме хранилищ, спроектированы без состояния: любой под может обслужить любой запрос, а всё состояние лежит во внешних хранилищах. Это позволяет масштабировать их добавлением подов. Ниже описаны механизмы и правила масштабирования.

1. **Горизонтальный автоскейлинг по метрикам нагрузки.** Для каждого сервиса настроен Horizontal Pod Autoscaler по метрике, которая действительно отражает нагрузку: для CPU-bound сервисов (BFF, Playback) — загрузка CPU с целевым значением 55–60 %, для I/O-bound сервисов (Telemetry Ingest) — число запросов в секунду на под. Потребители Kafka масштабируются через KEDA по лагу потребителя. Целевая загрузка ниже 60 % оставляет запас на время, пока поднимаются новые поды. Мы не используем память как метрику автоскейлинга для Go-сервисов, потому что она плохо коррелирует с нагрузкой.

2. **Предиктивное масштабирование перед пиками.** Реактивный автоскейлинг запаздывает на 1–3 минуты, а вечерний пик и премьеры предсказуемы. Поэтому планировщик на основе исторических данных за последние 4 недели выставляет минимальное число реплик (`minReplicas`) на 30 минут вперёд. Для запланированных премьер команда контента заводит событие в календаре мощностей, и система заранее масштабирует Playback, Entitlement, DRM и лицензионные серверы в 3 раза. Это стоит дешевле, чем отказы в первые минуты премьеры.

3. **Быстрый старт узлов и подов.** Karpenter выделяет узлы за 45–90 секунд, подбирая тип инстанса под ожидающие поды. Для дополнительного ускорения в каждом кластере держится резерв «балластных» подов с низким приоритетом, которые вытесняются при нехватке места для рабочих подов. Go-сервисы стартуют за 1–3 секунды, а образы контейнеров минимальны (20–40 МБ) и заранее закэшированы на узлах. В сумме это даёт реакцию на всплеск за 10–20 секунд при наличии резерва и за 2 минуты без него.

4. **Изоляция по пулам узлов.** Критичные сервисы воспроизведения работают на выделенном пуле узлов с зарезервированной ёмкостью (On-Demand и Savings Plans), без спотовых инстансов. Некритичные и пакетные нагрузки (рекомендации офлайн, транскодирование, аналитика) работают на спотовых инстансах, которые на 60–70 % дешевле. Это исключает ситуацию, когда массовое изъятие спотовых инстансов в облаке останавливает воспроизведение. Лимиты ресурсов и `PodDisruptionBudget` дополнительно защищают критичные сервисы.

5. **Ячейковое масштабирование.** Каждый регион разделён на ячейки, и в каждой ячейке работает полный набор сервисов плоскости управления со своими кэшами и очередями. Ячейка рассчитана примерно на 5 миллионов аккаунтов, так что на старте в крупнейшем регионе их 4, а в целом по системе — 10. Когда ячейка приближается к пределу, открывается новая, и в неё направляются новые регистрации, а при необходимости и часть существующих аккаунтов. Масштабирование ячейками ограничивает радиус поражения и позволяет тестировать предельную нагрузку одной ячейки, а не всей системы.

Маршрутизация в ячейку выполняется шлюзом без обращения к базе, по полю `cell` из JWT:

```go
// Маршрутизация запроса в ячейку по claim токена с fallback на согласованное хеширование.
func (r *CellRouter) Route(claims *Claims) string {
	if claims.Cell >= 0 && claims.Cell < len(r.cells) && r.cells[claims.Cell].Healthy() {
		return r.cells[claims.Cell].Upstream
	}
	// Токен старого формата без claim: детерминированно по account_id (rendezvous hashing).
	var best string
	var bestScore uint64
	for _, c := range r.cells {
		if !c.Healthy() {
			continue
		}
		h := xxhash.Sum64String(claims.AccountID + "|" + c.ID)
		if h > bestScore {
			best, bestScore = c.Upstream, h
		}
	}
	return best
}
```

## 5.3. Шардирование хранилищ

Каждое хранилище шардируется по ключу, который совпадает с основным паттерном доступа. Благодаря этому подавляющее большинство запросов обращается к одному шарду. Ниже описано шардирование каждого хранилища.

1. **PostgreSQL + Citus (идентичность и коммерция).** Данные сначала разделены по домашнему региону пользователя, а внутри региона Citus распределяет их на 64 логических шарда по хешу `account_id`, размещённых на 8 рабочих узлах. 64 шарда на 8 узлах позволяют без пере-шардирования вырасти до 64 узлов, просто перемещая шарды функцией `citus_rebalance_start()` без остановки записи. Все таблицы домена колоцированы, поэтому транзакции «подписка + счёт + платёж + outbox» выполняются на одном узле. Справочники (тарифы, цены) реплицируются на все узлы как reference tables.

2. **Cassandra (прогресс, история, рекомендации).** Данные распределяются по кольцу токенов по хешу ключа партиции (`profile_id` или `profile_id + month`), а виртуальные узлы (16 на физический узел) выравнивают распределение. Добавление узла автоматически забирает часть диапазонов токенов у соседей, и ручного пере-шардирования не требуется. Размер партиций контролируется моделью данных: история режется по месяцам, чтобы ни одна партиция не превышала 10 МБ. На старте в каждом регионе 36 узлов, а рост ёмкости обеспечивается добавлением узлов по 3 (по одному в каждую зону доступности).

3. **Valkey (кэш и эфемерное состояние).** Кластер Valkey делит ключевое пространство на 16 384 хеш-слота, распределённых между шардами. Для атомарных операций над данными одного аккаунта используются hash tags, например `cc:{account_id}`, чтобы связанные ключи попадали в один слот. В каждой ячейке работает 6–12 первичных шардов с репликами. Перераспределение слотов при добавлении шардов выполняется онлайн, без остановки сервиса.

4. **Kafka (события и телеметрия).** Масштаб топика определяется числом партиций: топик телеметрии в каждом регионе имеет 384 партиции, что с запасом покрывает 450 тысяч событий в секунду на регион при 2–3 тысячах событий в секунду на партицию для потребителя ClickHouse. Ключом партиции выбран `session_id`, поэтому события одной сессии упорядочены. Доменные топики с низким трафиком имеют 12–48 партиций и ключ по `account_id`. Число партиций выбирается заранее с запасом, потому что увеличение числа партиций нарушает упорядоченность по ключу.

5. **ClickHouse (аналитика).** Таблицы распределены по шардам через движок `Distributed` с ключом шардирования `cityHash64(session_id)`, а внутри шарда данные партиционированы по дате. Каждый шард имеет 2 реплики через ClickHouse Keeper. Горизонтальное масштабирование выполняется добавлением шардов: новые данные распределяются с учётом весов, а старые данные доживают свой TTL в 90 дней на старых шардах. Это избавляет от дорогого перемещения исторических данных.

6. **OpenSearch (поиск).** Индекс каждой локали невелик, поэтому он имеет 1–3 первичных шарда и масштабируется по чтению числом реплик, а не шардированием. Для пиковых 20 тысяч поисковых запросов в секунду на регион используются 3 реплики на 9 узлах. Индексы пересоздаются целиком из CDC каталога, а переключение выполняется атомарной сменой алиаса. Такая схема проще и надёжнее, чем онлайн-изменение шардирования.

7. **Объектное хранилище (видео).** S3 масштабируется автоматически, но имеет ограничение около 5 500 GET-запросов в секунду на префикс. Ключи объектов начинаются с хеш-префикса ассета (`/{hash[0:4]}/{asset_id}/v1/...`), поэтому нагрузка распределяется по тысячам префиксов. В любом случае origin видит только промахи кэш-щитов, то есть менее 1 % от 2 млн запросов сегментов в секунду. Горячий контент дополнительно реплицируется во все три региона, чтобы shield каждого региона читал из локального бакета.

Пример перебалансировки Citus при добавлении узлов:

```sql
-- Добавляем два рабочих узла и запускаем фоновую перебалансировку без блокировки записи.
SELECT citus_add_node('citus-worker-09.commerce.eu-central-1.internal', 5432);
SELECT citus_add_node('citus-worker-10.commerce.eu-central-1.internal', 5432);
SELECT citus_rebalance_start(rebalance_strategy := 'by_disk_size', shard_transfer_mode := 'force_logical');
-- Мониторинг прогресса.
SELECT * FROM citus_rebalance_status();
```

## 5.4. Репликация

| Хранилище | Внутри региона | Между регионами | Согласованность |
|-----------|----------------|-----------------|-----------------|
| PostgreSQL + Citus | Patroni: 1 синхронная + 1 асинхронная реплика в разных AZ | Асинхронная реплика для DR в соседнем регионе | Строгая в домашнем регионе |
| PostgreSQL (каталог) | 2 реплики | Логические реплики во всех регионах | Задержка < 5 с |
| Cassandra | RF=3 (по одной на AZ) | Multi-DC, RF=3 в каждом регионе | `LOCAL_QUORUM`, LWW между регионами |
| Valkey | Реплика на шард в другой AZ | Нет (эфемерные данные) | В пределах ячейки |
| Kafka | RF=3, `min.insync.replicas=2` | MirrorMaker 2 для доменных топиков | Упорядоченность внутри партиции |
| ClickHouse | 2 реплики на шард | Нет (данные региональные) | Итоговая |
| OpenSearch | 3 реплики | Независимые индексы в каждом регионе | Итоговая (из CDC) |
| S3 | 3+ AZ встроенно | Cross-Region Replication горячего контента и мастер-копий | Итоговая |

Репликация PostgreSQL внутри региона синхронна с одной репликой (`synchronous_standby_names = 'ANY 1 (...)'`), поэтому подтверждённая транзакция платежа не теряется при потере одной зоны доступности. Цена синхронной репликации — 1–2 мс задержки между зонами, что допустимо для записи. Межрегиональная реплика асинхронна: при катастрофической потере региона допускается потеря не более нескольких секунд записей (RPO < 5 с), и это обсуждено с бизнесом и отражено в разделе 6.

## 5.5. Многоуровневое кэширование

Кэш — главный инструмент достижения задержки меньше 100 мс, и он устроен в несколько уровней. Каждый уровень снимает нагрузку со следующего и обслуживает запросы быстрее.

1. **Кэш на клиенте.** Клиенты кэшируют конфигурацию, карточки тайтлов и изображения по заголовкам `Cache-Control` и `ETag`. Главная страница кэшируется на клиенте на 2 минуты и обновляется в фоне при возврате в приложение. Это полностью устраняет часть запросов, особенно при навигации «назад». Для ТВ-клиентов кэш изображений особенно важен из-за медленных сетевых стеков.

2. **Кэш на edge.** Публичные ответы каталога и изображения кэшируются в PoP edge-провайдера с ключом по локали и стране. Для снижения промахов используется `stale-while-revalidate`: пользователь получает немного устаревший ответ мгновенно, а edge обновляет его в фоне. Доля попаданий для каталожных эндпоинтов составляет 85–90 %. Инвалидация при изменении тайтла выполняется по суррогатным ключам (`Surrogate-Key: title-{id}`) за несколько секунд.

3. **Кэш в памяти процесса.** BFF и Catalog держат в памяти каждого пода горячий набор карточек (около 50 тысяч записей, 200–500 МБ) с TTL 60 секунд и подпиской на поток изменений каталога. Чтение из памяти занимает микросекунды и не требует сетевого вызова. Для борьбы с одновременными промахами используется singleflight: параллельные запросы одного ключа объединяются в один запрос к источнику. Это главный уровень для достижения p50 < 30 мс.

4. **Распределённый кэш Valkey.** Общий кэш ячейки хранит карточки, решения Entitlement, профили и предвычисленные главные страницы для fallback. Время жизни ключей рандомизируется (например, 10 минут ± 20 %), чтобы массовые истечения не создавали лавину промахов. При промахе в Valkey сервис идёт в базу и заполняет кэш по паттерну cache-aside. Доля попаданий превышает 95 %.

5. **Кэши видеосегментов.** Для видео работает отдельная иерархия: edge-appliance у провайдеров, затем региональный shield, затем origin. Appliance заранее заполняются популярным контентом в ночные часы по прогнозу популярности на следующий день. Shield объединяет одновременные промахи (request collapsing), так что при премьере миллион запросов первого сегмента превращается в один запрос к origin. В сумме доля попаданий по байтам превышает 97 %, а на appliance в пик — 98 %.

```go
// Кэш карточек с singleflight и рандомизированным TTL.
type TitleCache struct {
	local *ristretto.Cache[string, *catv1.Title]
	group singleflight.Group
	vk    valkey.Client
	src   CatalogSource
}

func (c *TitleCache) Get(ctx context.Context, id, locale string) (*catv1.Title, error) {
	key := "cat:title:" + id + ":" + locale
	if t, ok := c.local.Get(key); ok {
		return t, nil
	}
	v, err, _ := c.group.Do(key, func() (any, error) {
		if b, err := c.vk.Do(ctx, c.vk.B().Get().Key(key).Build()).AsBytes(); err == nil {
			t := new(catv1.Title)
			if proto.Unmarshal(b, t) == nil {
				return t, nil
			}
		}
		t, err := c.src.Load(ctx, id, locale)
		if err != nil {
			return nil, err
		}
		b, _ := proto.Marshal(t)
		ttl := 10*time.Minute + time.Duration(rand.Int63n(int64(2*time.Minute)))
		c.vk.Do(ctx, c.vk.B().Set().Key(key).Value(string(b)).Ex(ttl).Build())
		return t, nil
	})
	if err != nil {
		return nil, err
	}
	t := v.(*catv1.Title)
	c.local.SetWithTTL(key, t, 1, 60*time.Second)
	return t, nil
}
```

## 5.6. Масштабирование CDN и доставки видео

Пиковые 14 Тбит/с — это главный масштабный вызов системы, и он решается комбинацией собственных узлов и коммерческих CDN. Собственные appliance — это серверы с 2×100 Гбит/с сетевыми интерфейсами, NVMe-дисками на 300–500 ТБ и оптимизированным стеком отдачи (sendfile, kTLS). Они размещаются бесплатно внутри сетей крупных провайдеров, которым выгодно убрать видеотрафик со своих внешних стыков. Один appliance устойчиво отдаёт 80–90 Гбит/с. Для покрытия 70 % пика (около 10 Тбит/с) при целевой загрузке 60 % и резерве N+1 в каждой площадке нужно около 250 appliance в 80–100 площадках.

Остальные 30 % трафика и резерв обслуживают две коммерческие CDN. Их выбор посессионно делает steering-сервис: он учитывает QoE по каждой CDN для конкретного провайдера пользователя за последние 5 минут и текущую загрузку appliance. Если appliance в площадке загружен выше 80 %, новые сессии этого провайдера частично уходят на коммерческую CDN. Это «переливание» (overflow) позволяет не строить собственную ёмкость под абсолютный пик.

## 5.7. Масштабирование при премьерах

Премьера популярного сезона создаёт «эффект толпы»: миллионы пользователей одновременно запрашивают одни и те же первые сегменты, лицензии и карточки. Ниже описаны меры, которые применяются одновременно.

1. **Предварительный прогрев кэшей.** За 24–48 часов до премьеры все рендишены первых эпизодов проливаются на все appliance и в shield всех CDN. В момент выхода первый сегмент уже лежит на каждом edge-узле, и origin не получает никакой нагрузки. Статус прогрева отображается на дашборде премьеры. Если прогрев не завершён к T-2 часа, дежурный получает алерт.

2. **Предварительное масштабирование плоскости управления.** Playback, Entitlement, Concurrency, DRM и BFF масштабируются в 3 раза за час до премьеры по событию из календаря мощностей. Кэши Entitlement заранее заполняются для аккаунтов, которые добавили тайтл в «Мой список». Лицензионные серверы получают дополнительные реплики во всех регионах. После премьеры автоскейлинг постепенно возвращает ёмкость.

3. **Сглаживание уведомлений.** Push-уведомления о выходе сезона рассылаются не одновременно, а волнами в течение 15–30 минут с учётом часового пояса. Иначе рассылка на 20 миллионов устройств создаёт синхронный всплеск запросов. Приоритет отдаётся пользователям, которые явно подписались на напоминание. Это превращает острый пик в плато.

4. **Защита от синхронных повторов.** Клиентские SDK при ошибках делают повтор с экспоненциальной задержкой и полным случайным разбросом (full jitter). Сервер при перегрузке возвращает `503` с `Retry-After` с рандомизированным значением. Это предотвращает «метроном» из синхронных повторов, который может добить восстанавливающийся сервис. Бюджет повторов на клиенте ограничен тремя попытками.

5. **Статическая деградация главной страницы.** Если персонализация не успевает, BFF отдаёт главную страницу, где премьера стоит первой строкой, из предвычисленного кэша страны. Пользователь всё равно видит нужный тайтл и может начать просмотр. Персонализированные строки подгружаются позже. Метрика «доля деградированных ответов» отслеживается во время премьеры отдельно.

## 5.8. Альтернативы и почему не выбраны

1. **Вертикальное масштабирование баз данных.** Можно было бы держать аккаунты и биллинг в одном очень большом экземпляре PostgreSQL (например, на 192 vCPU и 1,5 ТБ RAM). Этого хватило бы по производительности на несколько лет, и это заметно проще шардирования. Но один экземпляр — это единая точка отказа для всех пользователей региона, а обслуживание (обновления мажорных версий, VACUUM больших таблиц) становится рискованным и медленным. Кроме того, у вертикального масштабирования есть жёсткий потолок, и его достижение потребует срочной миграции в самый неудобный момент.

2. **Шардирование по стране вместо хеша аккаунта.** Шардирование по стране выглядит естественным для лицензий и соответствия требованиям локализации данных. Однако страны сильно различаются по размеру: в одной могут быть 10 миллионов пользователей, в другой — 50 тысяч, что создаёт горячие шарды и неравномерную загрузку. Кроме того, пользователь может сменить страну. Мы используем регион как грубое разделение для требований к хранению данных и хеш аккаунта внутри региона для равномерности.

3. **Один большой кластер Kubernetes на регион вместо ячеек.** Один кластер проще в управлении и эффективнее по утилизации ресурсов. Но крупный кластер (более 5 000 узлов) приближается к пределам масштабируемости control plane Kubernetes, а неудачное изменение конфигурации (CNI, admission webhook, mesh) затрагивает всех пользователей региона. Ячейки ограничивают радиус поражения примерно 5 миллионами аккаунтов. Небольшая потеря эффективности утилизации окупается снижением риска крупных инцидентов.

4. **Реактивный автоскейлинг без предиктивной части.** Настройка только HPA проще и не требует модели прогнозирования. Но реактивный механизм запаздывает на минуты, а вечерний рост нагрузки идёт быстро, и премьеры дают ступенчатый скачок в первые секунды. Держать постоянный запас ×3 на весь день дорого: это десятки процентов лишних вычислительных затрат. Предиктивная часть с минимальным числом реплик по расписанию даёт запас именно тогда, когда он нужен.

5. **Только коммерческие CDN с собственными кэшами в облаке.** Можно было бы построить собственные кэши не у провайдеров, а в облачных регионах и точках присутствия облака. Но исходящий трафик из облака на таких объёмах стоит дорого, и такие кэши не приближают контент к пользователю сильнее, чем коммерческие CDN. Главный выигрыш appliance — размещение внутри сети провайдера, где трафик не пересекает стыки и не оплачивается как транзит. Облачные кэши не дают ни экономии, ни качества.

6. **Масштабирование Cassandra вертикально на крупных узлах.** Меньше крупных узлов означает меньше операционных задач. Однако у Cassandra время восстановления узла (streaming данных при замене) пропорционально объёму данных на узле, и узел с 10 ТБ восстанавливается сутками, что увеличивает окно уязвимости. Рекомендуемый объём — 1–2 ТБ на узел для баланса между числом узлов и временем восстановления. Поэтому мы держим 36 узлов среднего размера на регион.
