# 1. Общая архитектура

## 1.1. Ключевая идея: разделение плоскости управления и плоскости данных

Архитектура онлайн-кинотеатра строится вокруг одного факта: трафик управления и трафик видео отличаются на несколько порядков. Пользователь за вечер делает несколько сотен API-запросов общим объёмом в единицы мегабайт: открыть главную страницу, найти фильм, запросить лицензию, сохранить позицию просмотра. За тот же вечер он скачивает несколько гигабайт видеосегментов. Поэтому система делится на две независимые плоскости с разными требованиями, технологиями и командами.

**Плоскость управления (control plane)** — это микросервисы в трёх облачных регионах. Они отвечают за учётные записи, подписки, каталог, поиск, рекомендации, авторизацию воспроизведения, DRM-лицензии, историю просмотров и аналитику. Её главные показатели — задержка API (p99 < 100 мс), корректность данных и доступность. **Плоскость данных (data plane)** — это многоуровневая сеть доставки контента: собственные кэширующие серверы у интернет-провайдеров, коммерческие CDN, региональные кэши-щиты (origin shield) и объектное хранилище-источник. Её главные показатели — пропускная способность (14–20 Тбит/с), доля попаданий в кэш и время до первого байта сегмента.

Разделение даёт независимое масштабирование и изоляцию отказов. Если плоскость управления частично деградирует, уже начатые просмотры продолжаются: сегменты отдаются с кэшей, а подписанные URL и DRM-лицензии живут часами. Если деградирует одна CDN, steering-сервис плоскости управления переводит новые сессии на другую CDN.

## 1.3. Поток «Пользователь нажал “Смотреть”»

Самый важный сценарий системы — старт воспроизведения. Его бюджет времени определяет почти все архитектурные решения, поэтому ниже он разобран пошагово.

```
Клиент          Edge API     Gateway   Playback    Entitlement  Concurrency  Steering   DRM      CDN edge
  |  POST /playback/sessions  |           |            |            |           |         |          |
  |------------->|----------->|---------->|            |            |           |         |          |
  |              |            |  JWT ok   |--gRPC----->| (кэш 60 с) |           |         |          |
  |              |            |           |<--allowed--|            |           |         |          |
  |              |            |           |--gRPC------------------>| Lua в Valkey          |          |
  |              |            |           |<--slot granted----------|           |         |          |
  |              |            |           |--gRPC------------------------------>| score   |          |
  |              |            |           |<--[cdnA:0.7, cdnB:0.3] + edge hints--|         |          |
  |<-------------|<-----------|<----------| манифест-URL (подписан), license URL, токен    |          |
  |  GET master.m3u8 / manifest.mpd ---------------------------------------------------------------->|
  |  POST license (challenge) ---------------------------------------------------------->|          |
  |<-------------------------------------------------------------------------- лицензия |          |
  |  GET init.mp4, seg_00001.m4s ------------------------------------------------------------------->|
  |<----------------------------------------------------------------------------------- сегмент (hit)|
  |  первый кадр: цель p90 < 1,5 с от нажатия                                                         |
```

Бюджет по шагам выглядит так. Создание сессии воспроизведения занимает 60–90 мс end-to-end, из них 20–40 мс уходит на сеть от клиента до ближайшего edge. Загрузка манифеста с edge занимает 30–60 мс. Запрос DRM-лицензии обрабатывается в ближайшем регионе за 80–150 мс. Первый видеосегмент отдаётся с edge за 50–100 мс (TTFB), а полная загрузка сегмента низкого битрейта на старте занимает 150–400 мс. Декодирование и отрисовка первого кадра — 100–200 мс. Часть шагов идёт параллельно: плеер запрашивает лицензию одновременно с загрузкой init-сегмента. Итоговое время старта укладывается в целевые 1,5 секунды на p90.

## 1.4. Описание компонентов

Ниже описан каждый компонент: его ответственность, характер нагрузки и ключевые решения. Компоненты перечислены в порядке прохождения запроса от клиента вглубь системы.

1. **Клиентские приложения.** Web-клиент (TypeScript), приложения для iOS (Swift), Android (Kotlin), Smart TV (Tizen, webOS, Android TV) и консолей используют общий контракт с backend через BFF. Каждый клиент содержит плеер с адаптивным битрейтом: он выбирает качество по пропускной способности и заполненности буфера, а также переключает CDN при ошибках. Клиент отправляет пакетную телеметрию качества воспроизведения (время старта, ребуферизации, переключения битрейта, ошибки) раз в 30 секунд. Для ТВ-устройств без удобной клавиатуры используется device authorization flow: пользователь вводит короткий код на телефоне.

2. **Глобальный DNS и GSLB.** Authoritative DNS работает на Anycast-сети с несколькими провайдерами, чтобы отказ одного провайдера DNS не делал сервис недоступным. Для API используется маршрутизация по задержке с проверками здоровья регионов: если регион теряет здоровье, его записи исключаются за 30–60 секунд. Видеотрафик DNS не маршрутизирует: адрес конкретной CDN выдаёт steering-сервис в ответе на создание сессии. Так управление трафиком видео становится посессионным и мгновенным, без ожидания истечения TTL.

3. **Edge-слой API.** Запросы API приходят на Anycast-адреса edge-провайдера, где выполняются поглощение объёмных DDoS-атак, WAF-правила, bot management и терминация TLS 1.3 и QUIC. На edge кэшируются публичные неперсонализированные ответы: метаданные тайтлов, изображения, конфигурации клиентов. Это снимает с регионов до 40 % read-трафика каталога. От edge до региона запросы идут по постоянным соединениям через магистраль провайдера, что экономит 1–2 RTT на TLS-рукопожатиях.

4. **API Gateway.** В каждом регионе стоит кластер Envoy, который проверяет подпись JWT без обращения к сервису аутентификации, применяет распределённые лимиты запросов, маршрутизирует к BFF и добавляет заголовки трассировки. Шлюз ведёт себя как «тонкий»: бизнес-логики в нём нет, есть только сквозные политики. Для защиты от перегрузки шлюз сбрасывает нагрузку по приоритетам: запросы воспроизведения важнее рекомендаций, а рекомендации важнее телеметрии.

5. **BFF (Backend for Frontend).** Отдельные BFF для ТВ, мобильных устройств и Web агрегируют ответы нескольких доменных сервисов в один ответ, оптимизированный под устройство. Например, для ТВ главная страница содержит крупные изображения и меньше строк, а для мобильного устройства — компактные превью. BFF вызывают доменные сервисы параллельно через gRPC с жёсткими дедлайнами и возвращают частичный ответ, если некритичный сервис не ответил вовремя. Благодаря этому клиентские команды развивают экраны без изменения доменных сервисов.

6. **Identity & Auth.** Сервис выпускает и обновляет токены (OAuth 2.1 / OpenID Connect), поддерживает пароль, passkeys (WebAuthn), MFA и device flow. Access-токены короткоживущие (10 минут) и подписаны ES256, поэтому их проверяют локально по публичным ключам JWKS. Refresh-токены ротируются при каждом использовании, а повторное использование старого токена отзывает всё семейство токенов. Сервис пишет в шардированный кластер PostgreSQL, в котором данные пользователя хранятся в его домашнем регионе.

7. **Account & Profiles.** Сервис управляет учётной записью, профилями (до 5 на аккаунт), детскими профилями, языковыми настройками и устройствами. Нагрузка на него в основном читающая, и эти чтения закрываются кэшем Valkey с инвалидацией через события изменения. Изменения публикуются в Kafka через паттерн transactional outbox, чтобы остальные сервисы (рекомендации, биллинг, уведомления) узнавали о них надёжно. Удаление аккаунта запускает сагу, которая стирает персональные данные во всех хранилищах в соответствии с GDPR.

8. **Subscription & Billing.** Сервис ведёт тарифные планы, цены по странам, подписки, счета и платежи. С платёжными провайдерами он работает через токенизацию, поэтому номера карт никогда не попадают в систему, и область аудита PCI DSS остаётся минимальной. Все операции идемпотентны по ключу `Idempotency-Key`, а вебхуки провайдеров проверяются по подписи и дедуплицируются. Это единственный домен с требованием строгой согласованности, поэтому он работает только в домашнем регионе пользователя с синхронной репликацией внутри региона.

9. **Entitlement.** Сервис отвечает на вопрос «может ли этот профиль смотреть этот тайтл на этом устройстве в этой стране и в каком качестве». Решение учитывает статус подписки, тариф (максимальное разрешение, HDR, число потоков), лицензионные окна по странам, возрастной рейтинг профиля и уровень защиты DRM устройства. Ответы кэшируются на 60 секунд, а изменения подписки инвалидируют кэш событием. Сервис вызывается на каждом старте воспроизведения, поэтому его p99 ограничен 15 мс.

10. **Catalog Metadata.** Сервис хранит тайтлы, сезоны, эпизоды, локализации, персон, жанры, изображения, лицензионные окна, а также описания видеоассетов и дорожек. Каталог невелик (десятки гигабайт), но читается очень часто, поэтому он реплицирован во все регионы и закэширован на трёх уровнях: в памяти процесса, в Valkey и на edge. Запись идёт только через CMS в одном регионе, а изменения распространяются через CDC в Kafka. Для чтения сервис предоставляет пакетные gRPC-методы, чтобы BFF получал 40 карточек одним вызовом.

11. **Search.** Поиск по названиям, персонам и жанрам с учётом опечаток, транслитерации и морфологии работает на OpenSearch с отдельными индексами на каждую локаль. Индексы строятся из CDC-потока каталога с задержкой меньше минуты. Ранжирование сочетает текстовую релевантность с популярностью в стране пользователя и доступностью по лицензии. Подсказки при вводе обслуживаются отдельным лёгким индексом с префиксным поиском, чтобы укладываться в 30 мс.

12. **Recommender.** Персональные строки главной страницы («Продолжить просмотр», «Потому что вы смотрели…», «Топ-10 в вашей стране») строятся двухэтапно. Офлайн-модели (обучение на Spark и GPU) ежечасно генерируют кандидатов и кладут их в Cassandra. Онлайн-сервис на Go переранжирует кандидатов лёгкой моделью с учётом контекста: устройства, времени суток и последних действий. Если сервис недоступен, BFF показывает заранее посчитанную неперсонализированную главную страницу для страны, поэтому пользователь никогда не видит пустой экран.

13. **Playback Session.** Это оркестратор старта воспроизведения. Он проверяет право на просмотр, захватывает слот одновременных потоков, получает от steering-сервиса список CDN, формирует подписанные URL манифестов и возвращает клиенту URL лицензионного сервера с сессионным токеном. Сервис stateless, а состояние сессии живёт в Valkey с TTL и продлевается heartbeat-запросами. Это самый критичный сервис системы: для него действует отдельный SLO 99,99 %, выделенные узлы и приоритет при сбросе нагрузки.

14. **DRM License & Key Service.** Сервис выдаёт лицензии Widevine, FairPlay и PlayReady и проверяет сессионный токен, привязанный к сессии воспроизведения. Контентные ключи хранятся в отдельном Key Service в зашифрованном виде: они обёрнуты мастер-ключом из HSM-backed KMS и никогда не хранятся в открытом виде вне памяти. Лицензии задают политику: срок жизни, разрешение, HDCP, возможность офлайн-просмотра. Лицензионные серверы развёрнуты во всех трёх регионах, а ключи реплицируются между ними в зашифрованном виде.

15. **CDN Steering.** Сервис выбирает для каждой новой сессии упорядоченный список CDN и конкретных edge-кластеров. Выбор учитывает ASN провайдера пользователя, текущую загрузку собственных appliance, QoE-метрики каждой CDN за последние 5 минут и стоимость трафика. Данные о QoE поступают из телеметрии клиентов через Kafka и ClickHouse с задержкой меньше 60 секунд. При падении CDN её вес обнуляется, и новые сессии уходят на альтернативы, а уже идущие сессии переключаются самим плеером по резервному списку.

16. **Progress & History.** Сервис сохраняет позицию просмотра, историю, оценки и «Мой список». Позиция приходит вместе с heartbeat раз в 60 секунд, а при паузе и выходе отправляется немедленно. Всё это лежит в Cassandra, реплицированной между регионами, поэтому пользователь продолжает просмотр на другом устройстве с того же места. Запись идёт с уровнем согласованности `LOCAL_QUORUM`, а конфликты между регионами разрешаются по принципу last-write-wins по времени события.

17. **Concurrency.** Сервис ограничивает число одновременных потоков на аккаунт в соответствии с тарифом. Он реализован атомарным Lua-скриптом в Valkey над отсортированным множеством сессий с временными метками heartbeat. Просроченные сессии (без heartbeat дольше 3 минут) автоматически освобождают слот. Если Valkey недоступен, сервис переходит в режим fail-open с журналированием: мы сознательно предпочитаем временно пропустить лишний поток, чем отказать платящему пользователю.

18. **Telemetry Ingest.** Сервис принимает пакеты событий от плееров и приложений (около 1,3 млн событий в секунду в пике), валидирует их по схеме и пишет в Kafka. Это лёгкий асинхронный путь: клиент получает `202 Accepted` сразу после записи в Kafka. Из Kafka события расходятся в ClickHouse (оперативная QoE-аналитика и steering), в озеро данных Iceberg (исследования и обучение моделей) и в потоковую обработку (обнаружение аномалий и мошенничества). При перегрузке сервис сэмплирует некритичные события, но никогда не отбрасывает ошибки воспроизведения.

19. **Notification.** Сервис рассылает push-уведомления, e-mail и сообщения внутри приложения: о выходе новых эпизодов, о проблемах с оплатой, об изменениях безопасности аккаунта. Он потребляет доменные события из Kafka, применяет пользовательские настройки и частотные ограничения и отправляет сообщения через провайдеров (APNs, FCM, почтовый провайдер). Все отправки идемпотентны по ключу события, поэтому повторная доставка события из Kafka не создаёт дублей. Массовые рассылки идут через очередь с плавным темпом, чтобы не создать «эффект толпы» на API.

20. **Конвейер ингеста и транскодирования.** Мастер-копии от студий (IMF или ProRes) загружаются в изолированный бакет и проходят автоматический контроль качества. Далее для каждого тайтла анализируется сложность сцен (per-title или per-shot encoding), и он кодируется в лестницу из 10–14 ступеней трёх кодеков (H.264, HEVC, AV1). Затем результат упаковывается в CMAF, шифруется по CENC (схема `cbcs`) и публикуется в origin. Оркестрация построена на Temporal, а кодирование идёт на спотовых инстансах с разбиением видео на чанки по 30–60 секунд, поэтому двухчасовой фильм кодируется за 30–60 минут.

21. **Многоуровневая CDN.** Первый уровень — собственные кэширующие appliance внутри сетей крупных провайдеров, которые обслуживают около 70 % трафика, и две коммерческие CDN для остальных 30 % и для резерва. Второй уровень — региональные origin shield, которые коалесцируют промахи, так что один сегмент запрашивается из origin один раз, а не тысячей edge-узлов. Третий уровень — объектное хранилище S3. Популярный контент заранее «проливается» на appliance ночью (proactive fill), поэтому в вечерний пик доля попаданий в кэш на appliance превышает 98 %.

22. **Хранилища данных и аналитика.** PostgreSQL с Citus хранит данные, требующие транзакций, а отдельный PostgreSQL — каталог. Cassandra хранит данные с большим объёмом записи и простыми паттернами доступа, Valkey используется как кэш и для эфемерного состояния, OpenSearch — для поиска, Kafka — как шина событий и CDC. ClickHouse отвечает за оперативную аналитику, а S3 с Iceberg — за озеро данных. Подробное обоснование каждого выбора приведено в разделе 2, а схемы данных — в разделе 3.

## 1.5. Архитектурные принципы

Архитектура следует нескольким принципам, которые служат критериями при спорных решениях. Они записаны явно, чтобы новые команды принимали согласованные решения без централизованного согласования каждой детали.

1. **Воспроизведение важнее всего остального.** Если ресурсов не хватает, система жертвует рекомендациями, поиском, телеметрией и персонализацией, но не стартом и продолжением воспроизведения. Этот приоритет закодирован в классах сброса нагрузки на шлюзе, в выделенных пулах узлов для playback-сервисов и в стратегиях деградации BFF. Любой новый сервис при проектировании обязан ответить на вопрос, как его отказ повлияет на воспроизведение. Ответ «блокирует старт» требует отдельного архитектурного ревью.

2. **Ячейковая архитектура (cells).** Внутри региона сервисы развёрнуты в нескольких независимых ячейках, каждая обслуживает свой сегмент аккаунтов по хешу `account_id`. Отказ или неудачный релиз в одной ячейке затрагивает не более 1/N пользователей региона. Ячейки не делят ни базы данных, ни кэши, ни очереди, кроме глобально реплицированного каталога. Маршрутизация в ячейку выполняется на шлюзе по claim из JWT, без дополнительных сетевых вызовов.

3. **Асинхронность по умолчанию между доменами.** Синхронные gRPC-вызовы разрешены только на пути пользовательского запроса и только с дедлайнами. Всё остальное взаимодействие между доменами идёт через события в Kafka с гарантией at-least-once и идемпотентными потребителями. Это снижает связность и позволяет сервисам-потребителям отставать без влияния на пользователей. Для межсервисных бизнес-процессов (оформление подписки, удаление аккаунта) используются саги с компенсирующими действиями.

4. **Данные рядом с пользователем.** Данные, которые нужны для чтения на горячем пути (каталог, прогресс, права), реплицируются во все регионы. Данные со строгими требованиями к согласованности (платежи, пароли) живут в домашнем регионе, и запись туда маршрутизируется явно. Это позволяет обслуживать 99 % запросов из ближайшего региона. Путешествующий пользователь читает локально, а редкие записи в аккаунт делает с межрегиональной задержкой.

5. **Всё описано как код и всё наблюдаемо.** Инфраструктура, политики безопасности, алерты, дашборды и SLO хранятся в Git и применяются автоматически. Каждый сервис с первого дня экспортирует метрики RED, структурированные логи и трассировки OpenTelemetry. Сервис без SLO и runbook не допускается в продакшн. Эти требования проверяются автоматически в CI и через шаблон сервиса.

## 1.6. Границы доменов и владение

Система разбита на восемь доменов, у каждого из которых есть команда-владелец: «Идентичность и аккаунты», «Коммерция» (подписки и биллинг), «Контент» (каталог, CMS, ингест), «Открытие контента» (поиск и рекомендации), «Воспроизведение» (playback, DRM, concurrency, steering), «Доставка» (CDN и appliance), «Данные» (телеметрия, озеро, аналитика) и «Платформа» (Kubernetes, CI/CD, наблюдаемость, безопасность). Домен владеет своими данными: никакой другой сервис не читает его базы напрямую, только через API или события. Это правило жёсткое, и оно проверяется сетевыми политиками: у сервиса нет сетевого доступа к чужой базе данных. Такое разбиение позволяет примерно 30–40 командам работать параллельно.

## 1.7. Альтернативы и почему не выбраны

1. **Монолит вместо микросервисов.** Модульный монолит проще в разработке, отладке и развёртывании, и для команды до 50 человек он часто лучше. Однако при 50 млн пользователей и 30+ командах монолит становится узким местом по скорости релизов: каждое изменение требует координации и полного регрессионного тестирования. Профили нагрузки доменов различаются радикально: телеметрия пишет миллион событий в секунду, а биллинг — сотни транзакций, и масштабировать их вместе расточительно. Мы берём компромисс: крупные доменные сервисы, а не «наносервисы», и внутри домена допускаем модульный монолит.

2. **Единая коммерческая CDN без собственных appliance.** Этот вариант проще и быстрее запускается, и он используется на первых этапах дорожной карты. При объёме около 1 ЭБ в месяц даже по оптовой цене коммерческий трафик стоит в 2–3 раза дороже гибридной схемы (см. раздел 10). Кроме того, одна CDN — это единая точка отказа и слабая позиция в переговорах о цене. Собственные appliance у провайдеров также дают лучшее качество, потому что трафик не пересекает стыки между сетями.

3. **Один глобальный регион с CDN.** Один регион сильно упрощает согласованность данных и эксплуатацию. Но задержка API из Азии и Южной Америки до одного региона в США составляет 150–250 мс только на сеть, что нарушает требование p99 < 100 мс. Отказ единственного региона означает полную недоступность сервиса, а это несовместимо с SLO 99,99 % для воспроизведения. Три активных региона — это минимальное число, которое даёт и географическое покрытие, и кворум для глобальных решений.

4. **Полностью serverless-архитектура (функции и управляемые шлюзы).** Serverless снимает заботу об узлах и хорошо подходит для неравномерной нагрузки. Но при постоянной высокой нагрузке (сотни тысяч RPS круглосуточно) стоимость вызовов функций в 3–5 раз выше, чем у контейнеров на зарезервированных узлах. Холодные старты и ограничения на соединения с базами данных мешают стабильно выдерживать p99 < 100 мс. Serverless мы используем точечно: для обработчиков вебхуков, утилит ингеста и редких административных задач.

5. **Service mesh с «умными» маршрутами вместо BFF.** Можно было бы отдавать клиентам доменные API напрямую и агрегировать данные на клиенте. Это увеличивает число запросов с клиента (особенно болезненно для ТВ-устройств со слабыми CPU и медленными сетями) и жёстко связывает клиентские релизы с доменными API. GraphQL-федерация — ещё одна альтернатива, но она добавляет сложную инфраструктуру и затрудняет кэширование на edge. Тонкие BFF под каждый класс устройств оказываются проще и быстрее.

6. **Peer-to-peer доставка видео (WebRTC-mesh между зрителями).** P2P снижает нагрузку на CDN для популярного контента в прямом эфире. Для библиотеки по запросу с длинным хвостом контента выигрыш мал, а сложность и риски велики: приватность (зрители видят IP друг друга), расход батареи и трафика у пользователей, а также сложности с DRM. Кроме того, многие ТВ-платформы не поддерживают нужные API. Мы оставляем эту технологию как возможное направление для будущих прямых трансляций.
