# 7. Безопасность

## 7.1. Модель угроз

Безопасность онлайн-кинотеатра защищает три разных актива: учётные записи и платёжные данные пользователей, лицензированный контент правообладателей и доступность самого сервиса. У каждого актива свои противники и свои последствия компрометации. Модель угроз построена по методологии STRIDE для каждого компонента и пересматривается при каждом значимом изменении архитектуры. Ниже перечислены основные угрозы, которые определили меры защиты.

1. **Захват учётных записей (account takeover).** Злоумышленники массово проверяют пары логин–пароль из утечек других сервисов (credential stuffing), а затем продают доступ к аккаунтам. Для стримингового сервиса это одна из самых массовых угроз, потому что аккаунты легко монетизировать. Последствия — жалобы пользователей, возвраты платежей и репутационный ущерб. Защитой служат лимиты на вход, обнаружение ботов, проверка паролей по базам утечек, MFA, passkeys и уведомления о новых входах.

2. **Пиратство и утечка контента.** Цель пиратов — получить незашифрованное видео высокого качества и распространить его. Атаки включают извлечение ключей из программных CDM, захват экрана и HDMI-сигнала, повторное использование подписанных URL и перепродажу аккаунтов. Для правообладателей это главный риск, и договоры со студиями содержат обязательные требования к защите (например, аппаратный DRM для 4K). Защита многоуровневая: DRM, раздельные ключи по качеству, короткоживущие токены доступа к CDN, криминалистические водяные знаки и мониторинг утечек.

3. **Отказ в обслуживании (DDoS).** Объёмные атаки на сетевом уровне могут достигать терабит в секунду, а атаки на уровне приложения имитируют легитимные запросы к дорогим эндпоинтам (поиск, вход, создание сессий). Цели — вымогательство, конкурентная борьба или демонстрация силы, часто приуроченная к премьере. Защита строится на Anycast-поглощении, скраббинге, WAF, лимитах и адаптивном сбросе нагрузки. Важно, что атаки на API не должны влиять на доставку видео и наоборот.

4. **Мошенничество с платежами.** Злоумышленники используют украденные карты для оформления подписок, проверяют валидность карт мелкими платежами (card testing) и злоупотребляют пробными периодами. Последствия — штрафы платёжных систем за высокий уровень chargeback, вплоть до отключения приёма платежей. Защита включает 3-D Secure, скоринг рисков у провайдера, лимиты на добавление карт и дедупликацию пробных периодов по отпечатку устройства и метода оплаты. Мониторинг доли chargeback — отдельная бизнес-метрика.

5. **Компрометация внутренней инфраструктуры.** Сюда относятся атаки через цепочку поставки (заражённая зависимость, скомпрометированный образ контейнера), кража учётных данных инженеров, злоупотребление доступом инсайдером и ошибки конфигурации (публичный бакет S3). Последствия максимальны: доступ к данным всех пользователей и к ключам контента. Защита строится на принципах нулевого доверия, минимальных привилегиях, подписанных артефактах, короткоживущих учётных данных и полном аудите. Ни у одного человека нет постоянного доступа к продакшн-данным.

6. **Утечка персональных данных.** Персональные данные пользователей (e-mail, история просмотров, IP-адреса, платёжные токены) защищены законами (GDPR, CCPA, LGPD и локальными законами о данных). Утечка влечёт штрафы до 4 % годовой выручки и обязательные уведомления. История просмотров особенно чувствительна, потому что раскрывает предпочтения и привычки. Защита включает шифрование на уровне полей, минимизацию данных, псевдонимизацию в аналитике и crypto-shredding при удалении.

## 7.2. Аутентификация

Аутентификация пользователей построена на OAuth 2.1 и OpenID Connect, а собственный сервис Identity выступает сервером авторизации. Поддерживаются четыре способа входа: пароль (с хешированием argon2id с параметрами m=64 МБ, t=3, p=4), passkeys (WebAuthn) как рекомендуемый способ, одноразовый код на e-mail и device authorization flow для ТВ. При регистрации и смене пароля он проверяется по базе скомпрометированных паролей через k-анонимный запрос (передаются только первые 5 символов SHA-1), а пароли из утечек запрещены. MFA (TOTP или passkey как второй фактор) обязательна для действий повышенного риска: смены e-mail, удаления аккаунта, изменения метода оплаты.

Токены устроены следующим образом. Access-токен — это JWT, подписанный ES256, со сроком жизни 10 минут, содержащий `sub` (account_id), `did` (device_id), `reg` (домашний регион), `cell`, `plan` и `scope`. Refresh-токен — непрозрачная случайная строка из 256 бит со сроком жизни 90 дней, хранимая в базе только в виде хеша, и она ротируется при каждом использовании. Ключи подписи JWT ротируются каждые 30 дней, при этом старый ключ остаётся в JWKS ещё 24 часа. Приватные ключи хранятся в KMS, и подпись выполняется через KMS API либо через кэшированный в памяти ключ, расшифрованный при старте пода.

```go
// Проверка access-токена на шлюзе/в сервисах: локально, без сетевых вызовов.
type Verifier struct {
	keys     atomic.Pointer[map[string]*ecdsa.PublicKey] // обновляется из JWKS каждые 5 минут
	issuer   string
	audience string
	revoked  *RevocationFilter // bloom-фильтр отозванных device_id, рассылается через Kafka
}

func (v *Verifier) Verify(raw string) (*Claims, error) {
	tok, err := jwt.ParseWithClaims(raw, &Claims{}, func(t *jwt.Token) (any, error) {
		if t.Method.Alg() != "ES256" { // жёстко фиксируем алгоритм: защита от alg=none и подмены
			return nil, fmt.Errorf("unexpected alg %s", t.Method.Alg())
		}
		kid, _ := t.Header["kid"].(string)
		key, ok := (*v.keys.Load())[kid]
		if !ok {
			return nil, errors.New("unknown kid")
		}
		return key, nil
	},
		jwt.WithIssuer(v.issuer),
		jwt.WithAudience(v.audience),
		jwt.WithExpirationRequired(),
		jwt.WithLeeway(30*time.Second),
	)
	if err != nil || !tok.Valid {
		return nil, ErrUnauthenticated
	}
	c := tok.Claims.(*Claims)
	if v.revoked.MayContain(c.DeviceID) && v.revoked.ConfirmRevoked(c.DeviceID) {
		return nil, ErrDeviceRevoked
	}
	return c, nil
}
```

Отзыв доступа до истечения 10-минутного токена требуется при краже устройства, смене пароля и подозрении на компрометацию. Для этого сервис Identity публикует событие отзыва в Kafka, а все шлюзы и сервисы поддерживают bloom-фильтр отозванных устройств и аккаунтов за последние 10 минут. Фильтр маленький (десятки килобайт) и проверяется локально за наносекунды. Ложные срабатывания фильтра подтверждаются точной проверкой в Valkey.

Межсервисная аутентификация построена на mTLS с идентичностями SPIFFE, которые выдаёт Istio (в режиме ambient через ztunnel). Каждый сервис получает сертификат со сроком жизни 24 часа и идентичностью вида `spiffe://platform/ns/playback/sa/license-server`. Статических паролей между сервисами нет. Доступ сервисов к облачным ресурсам (S3, KMS) выдаётся через IAM-роли, привязанные к сервисным аккаунтам Kubernetes (IRSA), с короткоживущими учётными данными.

## 7.3. Авторизация

Авторизация разделена на три уровня с разными механизмами. Для пользовательских ресурсов действует правило владения: запрос к `/v1/profiles/{pid}/...` разрешён, только если профиль принадлежит аккаунту из токена. Эта проверка выполняется в каждом сервисе через общую библиотеку, а не только на шлюзе, в соответствии с принципом «не доверяй вызывающему». Для права на просмотр контента работает сервис Entitlement (атрибутивная модель: подписка, страна, лицензия, возраст, уровень DRM). Для внутренних и административных операций используется RBAC с политиками в Open Policy Agent.

```rego
# OPA: доступ к административному API CMS.
package cms.authz

import rego.v1

default allow := false

# Редакторы метаданных могут менять описания и изображения, но не лицензии.
allow if {
    input.subject.roles[_] == "catalog_editor"
    input.action in {"update_localization", "upload_artwork"}
    input.resource.type == "title"
}

# Изменение лицензионных окон: только роль rights_manager и только для своей территории.
allow if {
    input.subject.roles[_] == "rights_manager"
    input.action == "update_license_window"
    input.resource.country_code in input.subject.territories
}

# Публикация тайтла требует двух разных людей (принцип четырёх глаз).
allow if {
    input.action == "publish_title"
    input.subject.roles[_] == "content_publisher"
    input.resource.approved_by != input.subject.id
    input.resource.approved_by != ""
}
```

Доступ инженеров к продакшну устроен по принципу just-in-time. По умолчанию ни у кого нет доступа к продакшн-базам и узлам. Доступ запрашивается через систему заявок с указанием инцидента или задачи, одобряется вторым человеком и выдаётся на 1–4 часа через Teleport с полной записью сессии. Доступ к персональным данным пользователей дополнительно требует обоснования, привязанного к обращению в поддержку, и проходит ежеквартальный аудит.

## 7.4. Защита контента

Защита контента устроена многоуровнево, чтобы компрометация одного уровня не давала полного доступа к качественному видео. Ниже описаны уровни защиты от внешнего к внутреннему.

1. **Шифрование контента и мульти-DRM.** Все рендишены шифруются AES-128 по схеме CENC `cbcs` при упаковке, а ключи выдаются только через DRM-лицензию в защищённую среду устройства (CDM). Поддерживаются Widevine (Android, Chrome, Android TV), FairPlay (устройства Apple, Safari) и PlayReady (Windows, Xbox, многие Smart TV). Лицензия содержит политику: срок действия, максимальное разрешение, требование HDCP и запрет захвата экрана. Устройства с отозванными или скомпрометированными CDM блокируются по спискам отзыва DRM-систем.

2. **Раздельные ключи по уровню качества.** Для каждого ассета используются разные ключи для SD, HD, UHD и аудио. Устройство с программным DRM (Widevine L3) получает лицензию только на ключи SD и HD до 720p–1080p, а ключ UHD выдаётся только аппаратному DRM (L1, SL3000, аппаратный FairPlay) с HDCP 2.2. Поэтому даже извлечение ключа из взломанного программного CDM не даёт доступа к 4K. Это стандартное требование договоров с крупными студиями.

3. **Токены доступа к CDN.** URL манифеста содержит подписанный токен с ограничением по времени (6 часов), идентификатору сессии, пути ассета и, опционально, префиксу IP-адреса клиента. Edge-узлы проверяют подпись без обращения к origin, используя общий секрет, ротируемый ежедневно. Это не даёт использовать утёкшие ссылки на манифест в пиратских плеерах надолго и массово. Сегменты также проверяются по токену, переданному через путь или cookie.

```python
# Подпись URL для CDN (HMAC-SHA256), проверяется на edge без обращения к origin.
import base64, hashlib, hmac, json, time

def sign_cdn_url(base_url: str, path_prefix: str, session_id: str, key_id: str, secret: bytes,
                 ttl_s: int = 6 * 3600, ip_prefix: str | None = None) -> str:
    claims = {
        "p": path_prefix,                 # доступ только к файлам этого ассета
        "s": session_id,                  # для отзыва и аудита
        "exp": int(time.time()) + ttl_s,
        "kid": key_id,                    # ключи ротируются ежедневно; edge хранит текущий и предыдущий
    }
    if ip_prefix:
        claims["ip"] = ip_prefix          # /24 для IPv4, /48 для IPv6 — терпимо к смене адреса в сети
    body = base64.urlsafe_b64encode(json.dumps(claims, separators=(",", ":")).encode()).rstrip(b"=")
    sig = base64.urlsafe_b64encode(hmac.new(secret, body, hashlib.sha256).digest()).rstrip(b"=")
    return f"{base_url}{path_prefix}master.mpd?tok={body.decode()}.{sig.decode()}"
```

4. **Криминалистические водяные знаки.** Для 4K и премьерного контента применяется A/B-водяная разметка на уровне сегментов: каждый сегмент существует в двух вариантах с разными невидимыми метками, и каждой сессии выдаётся уникальная последовательность вариантов. Последовательность кодирует идентификатор сессии, и по пиратской копии длиной 10–15 минут можно установить, с какого аккаунта произошла утечка. Выбор варианта выполняется на edge по токену сессии, без увеличения нагрузки на плоскость управления. Цена решения — удвоение объёма хранения для размеченного контента, что ограничивает его применение премьерами и 4K.

5. **Контроль злоупотреблений аккаунтами.** Система отслеживает аномалии: одновременные просмотры из разных стран, десятки устройств на одном аккаунте, нетипично высокий объём просмотра, массовые лицензии на один ассет. Такие признаки характерны для перепродажи аккаунтов и пиратских рипов. Скоринговая модель в потоке событий выставляет риск-оценку, и при превышении порога аккаунт требует повторного входа или подтверждения. Жёсткие санкции (блокировка) применяются только после ручной проверки.

## 7.5. Шифрование

| Где | Что | Как |
|-----|-----|-----|
| Клиент — edge | Весь трафик API и видео | TLS 1.3 (и QUIC), HSTS с preload, только AEAD-шифры |
| Edge — регион | Трафик API | TLS 1.3 по частным соединениям, взаимная аутентификация edge |
| Между сервисами | gRPC и HTTP | mTLS (Istio ambient), сертификаты SPIFFE на 24 часа |
| Сервисы — хранилища | PostgreSQL, Cassandra, Valkey, Kafka | TLS 1.3 с проверкой сертификатов, аутентификация по сертификату |
| Хранилища на диске | Тома EBS, NVMe, S3 | AES-256 с ключами KMS (SSE-KMS для S3, шифрование томов) |
| Поля с персональными данными | E-mail, имя, телефон, IP | Шифрование на уровне приложения (AES-256-GCM), ключ на аккаунт (envelope encryption) |
| Контент | Видеосегменты | CENC `cbcs`, ключи в Key Service под KMS/HSM |
| Резервные копии | Все копии | Шифрование ключом отдельного аккаунта резервных копий |

Шифрование на уровне полей реализовано по схеме envelope encryption: у каждого аккаунта свой ключ данных (DEK), который хранится зашифрованным мастер-ключом (KEK) в KMS. При удалении аккаунта уничтожается только его DEK. После этого все копии персональных данных, включая резервные копии и логи, в которые могли попасть зашифрованные значения, становятся нечитаемыми. Это и есть crypto-shredding, который решает проблему «права на забвение» для неизменяемых резервных копий.

## 7.6. Защита от DDoS и злоупотреблений

Защита от DDoS построена эшелонированно, и каждый эшелон отсекает свой класс атак. Ниже описаны эшелоны от сети к приложению.

1. **Anycast и поглощение объёмных атак.** Все публичные адреса API и edge анонсируются по Anycast из сотен точек присутствия edge-провайдера с суммарной ёмкостью в сотни Тбит/с. Объёмная атака распределяется по всем точкам и поглощается без влияния на легитимный трафик. Атаки на уровнях L3/L4 (SYN flood, UDP amplification) фильтруются аппаратно на входе. Регионы облака дополнительно защищены облачным сервисом защиты от DDoS с командой реагирования.

2. **Сокрытие origin.** Регионы облака не принимают трафик API из интернета напрямую: входящие соединения разрешены только из диапазонов edge-провайдера и только с взаимной аутентификацией. Это исключает обход защиты атакой напрямую на origin. Origin видеохранилища доступен только для shield-узлов CDN через подписанные запросы. Публичные IP-адреса регионов не публикуются и регулярно проверяются на утечки.

3. **WAF и защита от ботов.** WAF применяет управляемые наборы правил (OWASP Top 10) и собственные правила для наших эндпоинтов, например блокирует аномальные размеры тел и недопустимые методы. Сервис обнаружения ботов анализирует отпечаток TLS (JA4), поведение и репутацию IP, чтобы отличить скрипты от реальных клиентов. Для подозрительного трафика на эндпоинтах входа и регистрации включается невидимая проверка (challenge) и CAPTCHA. Нативные приложения подтверждают подлинность через аттестацию платформы (App Attest, Play Integrity).

4. **Лимиты запросов на нескольких уровнях.** На edge действуют грубые лимиты по IP и подсети, на шлюзе — точные лимиты по аккаунту, устройству и эндпоинту в скользящем окне, а в сервисах — адаптивный лимит параллелизма. Для входа действуют жёсткие лимиты: 5 попыток на аккаунт за 15 минут и 20 попыток с IP за минуту с экспоненциальным наращиванием блокировки. Лимиты для ТВ-устройств за NAT крупных провайдеров учитывают, что за одним IP могут быть тысячи пользователей. Поэтому ключевой признак — аккаунт и устройство, а не IP.

5. **Защита дорогих эндпоинтов.** Эндпоинты с высокой стоимостью обработки (поиск, создание сессий воспроизведения, лицензии) защищены дополнительно: создание сессии требует валидного токена и выполняется не чаще 30 раз в минуту на устройство. Поиск кэширует популярные запросы и отбрасывает бессмысленные (слишком длинные, из случайных символов). Лицензионные запросы проверяют привязку к сессии и одноразовый nonce, поэтому их нельзя массово воспроизвести. Такая защита не даёт атакующему превратить небольшой поток запросов в большую нагрузку на базы.

```go
// Лимитер скользящего окна в Valkey (атомарно через Lua).
var slidingWindow = valkey.NewLuaScript(`
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count >= limit then
  local oldest = redis.call('ZRANGE', key, 0, 0, 'WITHSCORES')
  return {0, math.ceil((tonumber(oldest[2]) + window - now) / 1000)}
end
redis.call('ZADD', key, now, ARGV[4])
redis.call('PEXPIRE', key, window)
return {1, 0}
`)

func (l *Limiter) Allow(ctx context.Context, scope, id string, limit int, window time.Duration) (bool, int) {
	now := time.Now().UnixMilli()
	res, err := slidingWindow.Exec(ctx, l.vk, []string{"rl:{" + scope + ":" + id + "}"},
		[]string{strconv.FormatInt(now, 10), strconv.FormatInt(window.Milliseconds(), 10),
			strconv.Itoa(limit), strconv.FormatInt(now, 10) + ":" + randSuffix()}).ToArray()
	if err != nil {
		return true, 0 // fail-open: отказ лимитера не должен блокировать пользователей
	}
	allowed, _ := res[0].AsInt64()
	retry, _ := res[1].AsInt64()
	return allowed == 1, int(retry)
}
```

## 7.7. Соответствие требованиям и защита данных

Платформа должна соответствовать нескольким регуляторным режимам одновременно, и требования встроены в архитектуру, а не добавлены сверху. Ниже описаны основные режимы.

1. **PCI DSS.** Номера карт никогда не попадают в нашу инфраструктуру: платёжная форма загружается с домена провайдера (hosted fields), и мы получаем только токен. Это сужает область аудита до уровня SAQ A, то есть до платёжной страницы и её скриптов. Целостность скриптов платёжной страницы контролируется через CSP и Subresource Integrity, как того требует PCI DSS 4.0. Ежегодный аудит и ежеквартальное внешнее сканирование уязвимостей выполняются по графику.

2. **GDPR и аналогичные законы.** Пользователь может скачать свои данные и удалить аккаунт через интерфейс. Удаление запускает сагу, которая удаляет данные во всех доменах и уничтожает ключ шифрования аккаунта в течение 30 дней. Данные пользователей из ЕС хранятся в регионе eu-central-1 (домашний регион), а межрегиональная репликация персональных данных ограничена псевдонимизированными идентификаторами. Для каждой категории данных задан срок хранения, и автоматические задачи удаляют устаревшие записи.

3. **Требования правообладателей.** Договоры со студиями содержат приложения с требованиями к защите контента: уровни DRM для каждого разрешения, HDCP, водяные знаки, геоблокировка, аудит безопасности. Эти требования транслируются в политики Entitlement и лицензионного сервера и проверяются автоматическими тестами. Ежегодно проводится независимый аудит защиты контента. Невыполнение требований может привести к отзыву лицензии на контент, поэтому они имеют приоритет наравне с законом.

4. **Защита детей.** Детские профили ограничены по возрастному рейтингу на уровне сервиса Entitlement, а не только интерфейса, поэтому прямой запрос к API не обходит ограничение. Для детских профилей отключены персонализированная реклама и сбор данных для рекламных целей. Изменение детского профиля и снятие PIN требуют подтверждения владельцем аккаунта. Требования COPPA и аналогичных законов учтены в модели данных.

5. **Журналы аудита.** Все административные действия, доступы к персональным данным, изменения прав и конфигурации безопасности журналируются в неизменяемое хранилище с проверкой целостности (цепочка хешей). Журналы хранятся 7 лет и доступны только команде безопасности и аудиторам. Аномальные паттерны доступа (массовая выгрузка, доступ в нерабочее время) порождают алерты в SIEM. Это обеспечивает и расследование инцидентов, и соответствие требованиям SOC 2.

## 7.8. Безопасность цепочки поставки и разработки

Каждый артефакт, попадающий в продакшн, проходит проверяемую цепочку. Исходный код хранится в Git с обязательным ревью и подписанными коммитами. CI собирает образы в изолированных раннерах, генерирует SBOM (SPDX), сканирует зависимости и образы на уязвимости (Trivy, Grype), выполняет статический анализ (Semgrep, gosec) и поиск секретов (gitleaks). Образы подписываются через Sigstore cosign с аттестацией происхождения уровня SLSA 3. Admission-контроллер Kubernetes (Kyverno) не допускает к запуску неподписанные образы, образы из недоверенных реестров и поды с привилегиями.

## 7.9. Альтернативы и почему не выбраны

1. **Сессии на сервере (stateful cookies) вместо JWT.** Серверные сессии легко отозвать мгновенно, и в них не хранится лишняя информация на клиенте. Но каждая проверка сессии — это сетевой вызов к хранилищу сессий, что при 300 тысячах RPS создаёт горячую зависимость и добавляет задержку в каждый запрос. Кроме того, это усложняет межрегиональную работу: сессия должна быть доступна во всех регионах. Короткоживущие JWT с локальной проверкой и bloom-фильтром отзыва дают почти мгновенный отзыв без центральной зависимости.

2. **Долгоживущие access-токены (сутки и больше).** Долгие токены уменьшают число запросов обновления и упрощают клиентов. Но украденный токен остаётся действительным всё это время, а механизм отзыва придётся проверять на каждом запросе, что возвращает нас к серверным сессиям. 10-минутные токены ограничивают окно злоупотребления, а обновление раз в 10 минут создаёт незначительную нагрузку (около 30 тысяч RPS в пике). Это стандартный баланс для потребительских сервисов.

3. **Единая DRM-система вместо мульти-DRM.** Одна DRM-система уменьшила бы стоимость лицензирования и сложность. Но ни одна DRM не поддерживается всеми платформами: FairPlay работает только на устройствах Apple, Widevine недоступен в Safari на iOS, а многие ТВ поддерживают только PlayReady. Отказ от любой из трёх систем означает потерю значимой доли аудитории. Схема `cbcs` позволяет хранить один набор зашифрованных файлов для всех трёх систем, поэтому затраты на мульти-DRM сосредоточены только в лицензионном сервисе.

4. **Собственная защита от DDoS на своих серверах.** Построить собственную систему скраббинга теоретически возможно, но для поглощения атак в несколько Тбит/с нужна сетевая ёмкость, сопоставимая с крупным CDN-провайдером, и распределённая по всему миру. Это десятки миллионов долларов капитальных затрат и отдельная команда. Облачные и CDN-провайдеры предлагают эту ёмкость как сервис по несравнимо меньшей цене. Мы сосредотачиваемся на защите уровня приложения, которую знаем лучше провайдера.

5. **Самописная система авторизации вместо OPA.** Правила доступа можно реализовать в коде каждого сервиса, что быстрее для первой версии. Но правила оказываются разбросаны по десяткам сервисов на разных языках, их сложно аудировать и невозможно проверить централизованно. OPA позволяет хранить политики в Git, тестировать их модульными тестами и применять одинаково в сервисах, Kubernetes и CI. Для горячего пути воспроизведения мы используем специализированный сервис Entitlement, а OPA — для административных и инфраструктурных политик.

6. **Шифрование только на уровне диска без шифрования полей.** Шифрование дисков защищает от кражи физических носителей, но не от утечки через SQL-инъекцию, скомпрометированную учётную запись приложения или неосторожную выгрузку в логи. Шифрование на уровне полей защищает персональные данные даже при доступе к базе и даёт механизм crypto-shredding для резервных копий. Цена — невозможность искать по зашифрованным полям, что решается детерминированным HMAC для e-mail. Для чувствительных персональных данных эта цена оправдана.
