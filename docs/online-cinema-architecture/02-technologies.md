# 2. Выбор технологий

## 2.1. Критерии выбора

Каждая технология в этом разделе оценивалась по одним и тем же критериям, чтобы выбор был воспроизводимым, а не вкусовым. Критерии упорядочены по важности, и при конфликте побеждает более высокий.

1. **Соответствие профилю нагрузки.** Технология должна естественно решать конкретную задачу: например, хранилище для миллиона записей позиции просмотра в минуту должно быть оптимизировано под запись, а не под сложные JOIN. Мы оцениваем задержку p99 под целевой нагрузкой, а не средние показатели в бенчмарках. Решение, которое требует постоянной борьбы с собственной природой технологии, отвергается. Для каждого выбора ниже указан конкретный паттерн доступа, который он обслуживает.

2. **Доказанная эксплуатация на сопоставимом масштабе.** Мы предпочитаем технологии, которые публично эксплуатируются в компаниях с похожей нагрузкой: стриминговых сервисах, крупных социальных сетях и маркетплейсах. Это означает, что основные проблемы уже найдены, задокументированы и имеют известные решения. Новые и модные технологии допускаются только там, где у них нет зрелой альтернативы. Если сбой случится в 3 часа ночи, дежурный должен найти ответ в документации или в сообществе.

3. **Операционная стоимость и доступность специалистов.** Мы учитываем не только цену лицензий и инфраструктуры, но и то, сколько инженеров нужно для эксплуатации и насколько легко их нанять. Технология, которой владеют сотни тысяч инженеров, предпочтительнее нишевой при сопоставимых характеристиках. Управляемые облачные сервисы выбираются там, где их наценка меньше стоимости команды эксплуатации. Там, где наценка огромна при нашем объёме (например, у управляемого Kafka), мы эксплуатируем систему сами.

4. **Лицензия и риск привязки к поставщику.** Предпочтение отдаётся открытым лицензиям (Apache 2.0, BSD, MIT, PostgreSQL License) и проектам под управлением фондов (CNCF, Apache, Linux Foundation). После смены лицензий рядом проектов в 2023–2024 годах мы выбираем форки под открытыми лицензиями, например Valkey вместо Redis и OpenTofu как совместимую замену Terraform. Облачно-специфичные сервисы допускаются, если за ними стоит стандартный протокол (например, S3 API) и существует план миграции. Это снижает риск резкого роста цен и юридических ограничений.

5. **Совместимость с остальным стеком.** Каждая технология должна интегрироваться с нашей наблюдаемостью (OpenTelemetry, Prometheus), средой исполнения (Kubernetes) и системой безопасности (mTLS, Vault). Технология без экспорта метрик или без поддержки TLS требует обвязки, и эта обвязка учитывается как стоимость. Мы стремимся к небольшому числу технологий в каждой категории: одна реляционная СУБД, одно wide-column хранилище, один брокер. Каждая дополнительная технология должна обосновать своё существование.

## 2.2. Языки программирования

### Go — основной язык backend-сервисов

Go используется для всех сервисов на горячем пути: шлюзовых плагинов, BFF, Playback, Entitlement, Concurrency, Steering, Catalog, Progress и Telemetry Ingest. Выбор обусловлен предсказуемой задержкой (сборщик мусора с паузами меньше миллисекунды), малым потреблением памяти на запрос (горутины по 2–8 КБ), быстрой компиляцией в статический бинарник и первоклассной поддержкой gRPC и OpenTelemetry. Go прост в изучении, поэтому новый инженер начинает приносить пользу за 2–3 недели, а это критично для организации из 30+ команд. Экосистема облачной инфраструктуры (Kubernetes, Envoy control plane, Prometheus, etcd) написана на Go, так что платформенная команда и продуктовые команды говорят на одном языке.

Пример типичного обработчика gRPC с дедлайном и метриками:

```go
package entitlement

import (
	"context"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"

	pb "platform/gen/entitlement/v1"
)

var decisionLatency = prometheus.NewHistogramVec(prometheus.HistogramOpts{
	Name:    "entitlement_decision_seconds",
	Help:    "Время принятия решения о праве на просмотр",
	Buckets: []float64{.001, .002, .005, .01, .015, .025, .05, .1},
}, []string{"result"})

type Server struct {
	pb.UnimplementedEntitlementServiceServer
	cache    DecisionCache
	subs     SubscriptionReader
	licenses LicenseWindowReader
}

func (s *Server) Check(ctx context.Context, req *pb.CheckRequest) (*pb.CheckResponse, error) {
	start := time.Now()
	// Жёсткий внутренний бюджет: не больше 15 мс, даже если вызывающий дал больше.
	ctx, cancel := context.WithTimeout(ctx, 15*time.Millisecond)
	defer cancel()

	key := decisionKey(req.GetProfileId(), req.GetPlayableId(), req.GetCountry(), req.GetDeviceClass())
	if d, ok := s.cache.Get(key); ok {
		decisionLatency.WithLabelValues("cache_hit").Observe(time.Since(start).Seconds())
		return d, nil
	}

	sub, err := s.subs.Active(ctx, req.GetAccountId())
	if err != nil {
		return nil, status.Error(codes.Unavailable, "subscription lookup failed")
	}
	window, err := s.licenses.Window(ctx, req.GetPlayableId(), req.GetCountry())
	if err != nil {
		return nil, status.Error(codes.Unavailable, "license lookup failed")
	}

	resp := decide(sub, window, req)
	s.cache.Set(key, resp, 60*time.Second)
	decisionLatency.WithLabelValues(resp.GetResult().String()).Observe(time.Since(start).Seconds())
	return resp, nil
}
```

```python
from pyspark.sql import SparkSession, functions as F, Window

spark = SparkSession.builder.appName("candidate-generation").getOrCreate()

views = spark.read.format("iceberg").load("lake.playback.completed_views") \
    .where(F.col("event_date") >= F.date_sub(F.current_date(), 90))

co_views = (views.alias("a")
    .join(views.alias("b"), on="profile_id")
    .where(F.col("a.title_id") != F.col("b.title_id"))
    .groupBy(F.col("a.title_id").alias("src"), F.col("b.title_id").alias("dst"))
    .agg(F.countDistinct("profile_id").alias("weight")))

w = Window.partitionBy("src").orderBy(F.desc("weight"))
top_similar = co_views.withColumn("rank", F.row_number().over(w)).where("rank <= 100")

top_similar.writeTo("lake.reco.similar_titles").overwritePartitions()
```

## 2.3. Базы данных

### PostgreSQL 17 + Citus — аккаунты, подписки, биллинг, токены

Для данных, требующих ACID-транзакций, внешних ключей и сложных ограничений целостности, выбран PostgreSQL. Это аккаунты, профили, устройства, refresh-токены, подписки, счета и платежи. Объём этих данных — около 1–2 ТБ на 50 млн пользователей, но запись требует строгой согласованности: списание денег и продление подписки должны происходить атомарно. Расширение Citus распределяет таблицы по шардам по `account_id`, так что все данные одного аккаунта лежат на одном узле и транзакции остаются локальными. Каждый регион держит свой кластер Citus для пользователей с этим домашним регионом, а высокая доступность внутри региона обеспечивается Patroni с синхронной репликой в другой зоне доступности.

```sql
-- Распределение таблиц по account_id: все данные аккаунта на одном шарде.
SELECT create_distributed_table('accounts',      'account_id', shard_count => 64);
SELECT create_distributed_table('profiles',      'account_id', colocate_with => 'accounts');
SELECT create_distributed_table('subscriptions', 'account_id', colocate_with => 'accounts');
SELECT create_distributed_table('invoices',      'account_id', colocate_with => 'accounts');
-- Справочник тарифов мал и нужен везде: реплицируется на все узлы.
SELECT create_reference_table('plans');
SELECT create_reference_table('plan_prices');
```

### PostgreSQL 17 — каталог метаданных

Каталог (25 тысяч тайтлов, 150 тысяч воспроизводимых единиц, сотни тысяч локализаций и изображений) занимает десятки гигабайт и идеально ложится в один нешардированный PostgreSQL. Запись идёт только через CMS в основном регионе, а чтение — с логических реплик в каждом регионе и из многоуровневого кэша. Реляционная модель здесь естественна: тайтл, сезоны, эпизоды, дорожки, лицензионные окна связаны внешними ключами, и CMS нуждается в транзакционном редактировании. Изменения выгружаются через Debezium в Kafka и оттуда попадают в поисковые индексы, кэши и edge.

### Apache Cassandra 5.0 — прогресс, история, списки, рекомендации

Позиция просмотра обновляется примерно 67 тысяч раз в секунду в пике, история просмотров растёт до десятков терабайт, а доступ всегда идёт по ключу профиля. Это классический паттерн для wide-column хранилища: высокая скорость записи, линейное горизонтальное масштабирование, мультирегиональная репликация «из коробки» и отсутствие единой точки отказа. Cassandra эксплуатируется на таком профиле крупнейшими стриминговыми сервисами, а версия 5.0 добавила SAI-индексы, векторный тип и улучшенное сжатие. Мы используем `NetworkTopologyStrategy` с RF=3 в каждом из трёх регионов и `LOCAL_QUORUM` для чтения и записи.

### Valkey 8 (кластер) — кэш, сессии, лимиты, конкурентность

Valkey — открытый форк Redis под лицензией BSD, развиваемый Linux Foundation, с полной совместимостью протокола. Он используется как распределённый кэш (карточки каталога, решения Entitlement, профили), хранилище эфемерного состояния (сессии воспроизведения, слоты одновременных потоков), распределённый лимитер запросов и хранилище идемпотентных ключей. Операции выполняются за доли миллисекунды, а Lua-скрипты дают атомарность составных операций без распределённых блокировок. В каждой ячейке каждого региона работает свой кластер из 6–12 шардов с репликой в другой зоне доступности.

### OpenSearch 2.x — поиск

Для полнотекстового поиска с морфологией (русский, английский, испанский, португальский, японский и другие языки), опечатками и фасетами выбран OpenSearch — открытый форк Elasticsearch под Apache 2.0. Индексы небольшие (сотни тысяч документов на локаль), поэтому кластер из 6–9 узлов на регион выдерживает пиковые 15–20 тысяч поисковых запросов в секунду с p99 < 50 мс. Документы индекса денормализованы: в одном документе есть название, персоны, жанры, популярность и страны доступности. Переиндексация без простоя выполняется через алиасы.

### ClickHouse — оперативная аналитика качества

ClickHouse принимает поток телеметрии плееров (около 1,3 млн событий в секунду) и отвечает на аналитические запросы за секунды: доля ребуферизации по CDN и провайдеру за последние 5 минут, время старта по моделям ТВ, ошибки DRM по версии приложения. Колоночное хранение со сжатием в 10–20 раз и материализованные представления делают его в десятки раз дешевле универсальных решений для этой задачи. Те же данные питают steering-сервис и дашборды качества. Долгосрочная история (дольше 90 дней) хранится только в озере данных.

```sql
-- ClickHouse: доля ребуферизации по CDN и ASN за последние 5 минут.
SELECT cdn, isp_asn,
       sum(rebuffer_ms) / sum(watch_ms) AS rebuffer_ratio,
       count() AS sessions
FROM qoe.playback_minute
WHERE ts >= now() - INTERVAL 5 MINUTE
GROUP BY cdn, isp_asn
HAVING sessions > 500
ORDER BY rebuffer_ratio DESC
LIMIT 50;
```

### Temporal — долгие рабочие процессы и оркестрация

Транскодирование фильма, оформление подписки с ретраями платежа, удаление аккаунта по GDPR и пролив контента на appliance — это многошаговые процессы длительностью от минут до недель. Им нужны надёжные ретраи, таймеры и компенсации. Temporal даёт durable execution: код рабочего процесса пишется как обычная функция на Go или Python, а платформа гарантирует его завершение при падениях воркеров. Это заменяет самописные конечные автоматы поверх очередей, которые являются типичным источником ошибок. Temporal работает на своём кластере с Cassandra в качестве хранилища.

```python
# Temporal workflow ингеста: каждый шаг ретраится независимо, состояние сохраняется.
from datetime import timedelta
from temporalio import workflow
from temporalio.common import RetryPolicy

@workflow.defn
class IngestWorkflow:
    @workflow.run
    async def run(self, asset_id: str) -> str:
        retry = RetryPolicy(maximum_attempts=5, backoff_coefficient=2.0)
        await workflow.execute_activity("quality_check", asset_id,
            start_to_close_timeout=timedelta(hours=2), retry_policy=retry)
        ladder = await workflow.execute_activity("analyze_complexity", asset_id,
            start_to_close_timeout=timedelta(hours=1), retry_policy=retry)
        chunks = await workflow.execute_activity("split_by_scenes", asset_id,
            start_to_close_timeout=timedelta(minutes=30), retry_policy=retry)
        # Параллельное кодирование чанков на спотовых узлах.
        await workflow.wait_all([
            workflow.execute_activity("encode_chunk", {"chunk": c, "ladder": ladder},
                start_to_close_timeout=timedelta(hours=1), retry_policy=retry)
            for c in chunks
        ])
        await workflow.execute_activity("package_and_encrypt", asset_id,
            start_to_close_timeout=timedelta(hours=1), retry_policy=retry)
        await workflow.execute_activity("publish_and_prewarm", asset_id,
            start_to_close_timeout=timedelta(minutes=30), retry_policy=retry)
        return "published"
```

## 2.5. Хранилище и видеостек

### Amazon S3 — источник видео (origin) и озеро данных

Объектное хранилище с долговечностью 11 девяток — естественный выбор для 10 ПБ видео. Классы хранения автоматизируют экономию: популярные рендишены лежат в Standard, длинный хвост — в Standard-IA, мастер-копии — в Glacier Deep Archive. S3 API стал отраслевым стандартом, поэтому origin можно перенести в другое облако или на собственное хранилище (MinIO, Ceph) без изменения кода. Озеро данных хранится там же в формате Apache Iceberg, который даёт ACID-транзакции над файлами Parquet и эволюцию схемы.

### CMAF + HLS/DASH, кодеки H.264/HEVC/AV1, DRM через CENC

Единый формат сегментов CMAF (фрагментированный MP4) обслуживает и HLS (Apple), и DASH (все остальные) из одних и тех же файлов, что вдвое сокращает объём хранилища и кэша по сравнению с раздельными форматами. H.264 нужен для совместимости со старыми устройствами, HEVC — для 4K HDR на ТВ и устройствах Apple, AV1 — для экономии 30–40 % трафика на современных устройствах. Шифрование по схеме CENC `cbcs` поддерживается всеми тремя DRM-системами, поэтому один зашифрованный файл работает с Widevine, FairPlay и PlayReady.

## 2.6. Инфраструктура исполнения

Всё исполняется в Kubernetes (Amazon EKS) на узлах Graviton (arm64), которые на 20–30 % дешевле x86 при той же производительности для Go-сервисов. Узлы выделяются через Karpenter, сетевой уровень и политики — Cilium (eBPF), взаимный TLS между сервисами обеспечивает Istio в режиме ambient (без sidecar-контейнеров). Инфраструктура описывается в OpenTofu, а развёртывание приложений выполняется по GitOps через Argo CD. Секреты хранятся в HashiCorp Vault, а ключи шифрования — в AWS KMS с HSM. Подробности приведены в разделе 9.

## 2.8. Альтернативы и почему не выбраны

1. **Java/Kotlin на JVM вместо Go для backend.** JVM-экосистема зрелая, а Spring и Micronaut дают богатую функциональность, и крупные стриминговые компании успешно на ней работают. Однако JVM-сервисы требуют больше памяти на под (обычно 512 МБ – 2 ГБ против 50–200 МБ у Go) и заметного времени прогрева, что снижает эффективность автоскейлинга при резких пиках. Настройка сборщика мусора для стабильного p99 на JVM — отдельная экспертиза. Kotlin мы используем в Android-клиентах, а на backend выигрыш Go в простоте и потреблении ресурсов перевешивает.

2. **Rust вместо Go.** Rust даёт ещё более предсказуемую задержку (без сборщика мусора) и безопасность памяти, и он отлично подходит для edge-кэшей и сетевых прокси. Но кривая обучения значительно круче, скорость разработки бизнес-логики ниже, а рынок найма уже в несколько раз. Для сервисов, где 95 % времени уходит на сетевые вызовы и работу с базой, выигрыш Rust в задержке несущественен. Мы допускаем Rust точечно: в модулях кэширующих appliance и в высоконагруженных прокси, если профилирование покажет узкое место.

3. **CockroachDB, YugabyteDB или Google Spanner вместо PostgreSQL + Citus.** Распределённые SQL-базы с глобальной согласованностью избавляют от ручного шардирования и позволяют писать из любого региона. Их цена — задержка записи (консенсус между регионами добавляет 50–150 мс), более высокая стоимость и, у CockroachDB, коммерческая лицензия для компаний нашего размера. Spanner привязывает к Google Cloud, а мы выбрали AWS как основное облако. Наш паттерн «аккаунт живёт в домашнем регионе» хорошо ложится на региональные кластеры Citus, и глобальный консенсус нам не нужен.

4. **ScyllaDB или DynamoDB вместо Cassandra.** ScyllaDB совместима с Cassandra по протоколу и быстрее на том же железе, но в конце 2024 года сменила модель лицензирования на source-available с ограничениями, что противоречит критерию 4. DynamoDB полностью управляемая и с глобальными таблицами, но при 67 тысячах записей в секунду в пике и десятках терабайт данных стоит в 3–4 раза дороже самоуправляемой Cassandra и жёстко привязывает к AWS. Cassandra 5.0 с открытой лицензией Apache и огромной базой эксплуатации — сбалансированный выбор.

5. **Redis (оригинальный) или Memcached вместо Valkey.** Redis после смены лицензии в 2024 году (RSAL/SSPL, затем AGPL для новых версий) создаёт юридическую неопределённость для коммерческого использования в облаке. Valkey полностью совместим по протоколу и развивается крупными облачными провайдерами, так что миграция в любую сторону тривиальна. Memcached проще и быстрее для чистого кэша, но у него нет структур данных (отсортированных множеств, Lua-скриптов), нужных для лимитеров и контроля конкурентности. Держать две технологии кэша ради маргинального выигрыша нецелесообразно.

6. **RabbitMQ, Apache Pulsar или NATS вместо Kafka.** RabbitMQ хорош для классических очередей задач, но не рассчитан на миллион событий в секунду с долговременным хранением и повторным чтением. Pulsar архитектурно интересен (разделение хранения и вычислений, встроенная георепликация), но его экосистема и база специалистов заметно меньше, а эксплуатация сложнее из-за BookKeeper. NATS JetStream лёгок и быстр, но ему не хватает зрелых коннекторов CDC и интеграций с аналитикой. Kafka — отраслевой стандарт для этого класса задач.

7. **Elasticsearch вместо OpenSearch.** Elasticsearch функционально богаче в ряде областей и вернул открытую лицензию AGPL в 2024 году. Однако AGPL накладывает обязательства, которые юристы многих компаний считают рискованными, а OpenSearch под Apache 2.0 развивается Linux Foundation и полностью покрывает наши потребности. Наш поисковый сценарий (сотни тысяч документов, морфология, опечатки) не требует продвинутых возможностей Elasticsearch. Для векторного поиска в рекомендациях возможности OpenSearch k-NN также достаточны.

8. **Snowflake или BigQuery вместо ClickHouse и Iceberg.** Облачные хранилища данных дают отличный опыт аналитиков и не требуют эксплуатации. При нашем объёме телеметрии (сотни терабайт в месяц до сжатия) и постоянных запросах от steering-сервиса каждые 10–30 секунд стоимость вычислений в модели «плата за запрос» становится очень высокой. ClickHouse отвечает на оперативные запросы за доли секунды при фиксированной стоимости кластера. Iceberg даёт открытый формат, который читают Spark, Trino, Flink и при необходимости сам Snowflake, поэтому возможность перейти на облачное хранилище сохраняется.
