# 9. CI/CD и инфраструктура

## 9.1. Принципы

Инфраструктура и процесс доставки изменений спроектированы так, чтобы 30–40 команд могли выпускать изменения в продакшн много раз в день без координации между собой и без роста числа инцидентов. Это возможно только при полной автоматизации и воспроизводимости. Ниже перечислены принципы, которые лежат в основе всех решений раздела.

1. **Всё описано как код.** Облачные ресурсы, кластеры Kubernetes, развёртывания сервисов, политики безопасности, алерты, дашборды и SLO описаны декларативно и хранятся в Git. Ручные изменения в консоли облака запрещены политиками IAM для всех, кроме аварийной роли с полным аудитом. Это делает любое окружение воспроизводимым и превращает Git-историю в журнал изменений инфраструктуры. Дрейф конфигурации обнаруживается ежедневной задачей и автоматически сообщается владельцу.

2. **GitOps: Git — единственный источник истины о желаемом состоянии.** Развёртывание — это изменение в Git-репозитории окружения, а не команда, выполненная из CI или с ноутбука. Контроллер Argo CD в каждом кластере непрерывно приводит фактическое состояние к описанному в Git. Откат — это `git revert`. CI не имеет учётных данных для доступа к продакшн-кластерам, что резко снижает риски компрометации конвейера.

3. **Неизменяемые артефакты.** Один и тот же образ контейнера, собранный один раз и идентифицированный по дайджесту, проходит все окружения от тестового до продакшна. Различается только конфигурация окружения. Пересборка образа для продакшна запрещена. Это гарантирует, что в продакшне работает ровно то, что было протестировано.

4. **Прогрессивная доставка.** Изменение никогда не попадает ко всем пользователям одновременно. Оно проходит этапы: канарейка в одной ячейке, вся ячейка, один регион, все регионы, и на каждом этапе автоматический анализ метрик решает, продолжать ли раскатку. Функциональность дополнительно скрыта за флагами функций, которые включаются отдельно от развёртывания кода. Это разделяет риск «выкатили код» и риск «включили поведение».

5. **Золотой путь (paved road).** Платформенная команда предоставляет шаблон сервиса, который по умолчанию включает CI-конвейер, Dockerfile, Helm-чарт, метрики, трассировки, логи, SLO, алерты, дашборд и runbook. Новый сервис создаётся одной командой во внутреннем портале разработчика (Backstage) и через час уже развёрнут в тестовом окружении. Команды могут отклониться от золотого пути, но тогда они сами несут ответственность за эквивалентные гарантии. На практике более 90 % сервисов остаются на золотом пути.

## 9.2. Структура облачных аккаунтов и сетей

Облачные ресурсы разделены на аккаунты по назначению и окружению через AWS Organizations: аккаунты продакшна по доменам (идентичность, коммерция, воспроизведение, контент, данные, платформа), отдельные аккаунты для staging и разработки, отдельный аккаунт для резервных копий, отдельный аккаунт для журналов аудита и отдельный аккаунт безопасности. Политики управления (SCP) запрещают отключение журналирования, создание публичных бакетов и использование регионов, не входящих в список разрешённых. Разделение аккаунтов ограничивает радиус поражения при компрометации учётных данных и упрощает распределение затрат по доменам.

Сети каждого региона построены по схеме hub-and-spoke через Transit Gateway: VPC каждого домена подключены к центральному хабу с инспекцией трафика. Межрегиональная связность идёт по магистрали облака. Для приватного доступа к управляемым сервисам (S3, KMS) используются VPC endpoints, поэтому трафик к ним не выходит в интернет. Адресное пространство спланировано заранее на 5 лет роста без пересечений.

## 9.3. Инфраструктура как код

Инфраструктура описывается в OpenTofu (открытый форк Terraform, совместимый с ним по языку и провайдерам), а для композиции окружений используется Terragrunt. Код организован в модули (VPC, кластер EKS, кластер PostgreSQL, бакет с политиками) и в «живые» конфигурации окружений, которые эти модули используют. Изменения проходят через pull request, где автоматически выполняются `tofu plan`, проверка политик (Checkov, OPA Conftest) и оценка изменения стоимости (Infracost). Применение изменений в продакшне выполняет Atlantis после одобрения владельцем.

```hcl
# modules/eks-cell/main.tf — одна ячейка: кластер EKS с пулами узлов для разных классов нагрузки.
module "eks" {
  source          = "terraform-aws-modules/eks/aws"
  version         = "~> 20.0"
  cluster_name    = "${var.region_short}-${var.cell_id}"
  cluster_version = "1.31"
  vpc_id          = var.vpc_id
  subnet_ids      = var.private_subnet_ids   # три зоны доступности

  cluster_endpoint_public_access = false
  enable_irsa                    = true

  cluster_encryption_config = {
    resources        = ["secrets"]
    provider_key_arn = var.kms_key_arn
  }

  eks_managed_node_groups = {
    # Системный пул: Karpenter, CoreDNS, Istio ztunnel, коллекторы.
    system = {
      instance_types = ["m7g.xlarge"]
      min_size       = 3
      max_size       = 6
      labels         = { "node-class" = "system" }
      taints         = [{ key = "CriticalAddonsOnly", value = "true", effect = "NO_SCHEDULE" }]
    }
  }

  tags = merge(var.tags, { cell = var.cell_id, cost_center = "platform" })
}

# Karpenter NodePool для критичных сервисов воспроизведения: только on-demand, только Graviton.
resource "kubectl_manifest" "nodepool_playback" {
  yaml_body = yamlencode({
    apiVersion = "karpenter.sh/v1"
    kind       = "NodePool"
    metadata   = { name = "playback-critical" }
    spec = {
      template = {
        metadata = { labels = { "node-class" = "playback-critical" } }
        spec = {
          requirements = [
            { key = "karpenter.sh/capacity-type", operator = "In", values = ["on-demand"] },
            { key = "kubernetes.io/arch",         operator = "In", values = ["arm64"] },
            { key = "karpenter.k8s.aws/instance-family", operator = "In", values = ["c7g", "c8g", "m7g"] },
          ]
          taints       = [{ key = "workload", value = "playback", effect = "NoSchedule" }]
          nodeClassRef = { group = "karpenter.k8s.aws", kind = "EC2NodeClass", name = "default" }
        }
      }
      limits     = { cpu = "4000" }
      disruption = { consolidationPolicy = "WhenEmpty", consolidateAfter = "10m" }
    }
  })
}
```

## 9.4. Контейнеры

Все сервисы упаковываются в минимальные образы: Go-сервисы собираются в статический бинарник и помещаются в образ distroless (без оболочки и пакетного менеджера), Python-сервисы используют slim-образ с фиксированными версиями зависимостей. Образы собираются для архитектур arm64 (основная, Graviton) и amd64 (резерв и узлы с GPU). Контейнеры запускаются от непривилегированного пользователя с корневой файловой системой только для чтения и без Linux capabilities. Размер типичного Go-образа — 20–35 МБ, что ускоряет развёртывание и автоскейлинг.

```dockerfile
# syntax=docker/dockerfile:1.7
FROM --platform=$BUILDPLATFORM golang:1.23 AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w -X main.version=${VERSION}" -o /out/service ./cmd/playback

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/service /service
USER nonroot:nonroot
EXPOSE 8080 9090
ENTRYPOINT ["/service"]
```

## 9.5. Оркестрация

Kubernetes (Amazon EKS) — единая среда исполнения для всех сервисов плоскости управления, конвейеров данных и ML-инференса. В каждом регионе работает по кластеру на ячейку (от 2 до 4 ячеек на регион), плюс отдельный кластер для общих региональных сервисов (каталог, поиск, лицензионные серверы, Kafka-потребители), кластер для пакетных задач (транскодирование, Spark) и кластер наблюдаемости. Всего на старте около 20 кластеров. Кластеры одинаковы по конфигурации и создаются из одного модуля, поэтому новая ячейка поднимается за несколько часов.

Базовые компоненты каждого кластера устанавливаются через Argo CD из общего репозитория платформы: Karpenter (выделение узлов), Cilium (сеть и сетевые политики на eBPF), Istio в режиме ambient (mTLS и L7-политики), External Secrets Operator (синхронизация секретов из Vault), cert-manager, Kyverno (политики допуска), KEDA (автоскейлинг по событиям), коллекторы OpenTelemetry и Argo Rollouts. Stateful-системы с большими требованиями к диску (Cassandra, Kafka, ClickHouse) работают на выделенных инстансах с локальными NVMe через операторы (K8ssandra, Strimzi, Altinity), а PostgreSQL — на выделенных инстансах под управлением Patroni вне Kubernetes. Такое решение принято, чтобы изолировать базы от изменений в кластерах приложений.

## 9.6. CI-конвейер

Код продуктовых сервисов живёт в монорепозитории на Go с Bazel для инкрементальной сборки и удалённым кэшем. Это позволяет пересобирать и тестировать только сервисы, затронутые изменением. CI выполняется в GitHub Actions на самостоятельно размещённых раннерах в Kubernetes (Actions Runner Controller) с эфемерными подами на каждое задание. Цель по времени — не больше 10 минут от push до готового к развёртыванию артефакта для типичного изменения.

```yaml
# .github/workflows/service.yml — конвейер сервиса (упрощённо).
name: service-ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write          # OIDC для подписи образов и доступа к реестру без статических ключей
  packages: write

jobs:
  test:
    runs-on: arc-runners-arm64
    steps:
      - uses: actions/checkout@v4
      - name: Определить затронутые цели
        run: bazel query "rdeps(//..., set($(git diff --name-only origin/main... | xargs)))" > targets.txt
      - name: Линтеры и статический анализ
        run: |
          bazel run //tools:golangci-lint -- run ./...
          semgrep ci --config p/golang --config .semgrep/
          gitleaks detect --no-banner
      - name: Проверка совместимости Protobuf
        run: buf breaking --against '.git#branch=main'
      - name: Модульные тесты
        run: bazel test $(cat targets.txt) --test_output=errors
      - name: Интеграционные тесты (testcontainers: PostgreSQL, Cassandra, Valkey, Kafka)
        run: bazel test //... --test_tag_filters=integration --test_output=errors
      - name: Контрактные тесты (Pact) с потребителями API
        run: bazel run //tools:pact-verify

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: arc-runners-arm64
    steps:
      - uses: actions/checkout@v4
      - name: Сборка мультиархитектурного образа
        run: bazel run //services/playback:push -- --tag ${{ github.sha }}
      - name: Сканирование уязвимостей
        run: trivy image --exit-code 1 --severity CRITICAL,HIGH $REGISTRY/playback:${{ github.sha }}
      - name: SBOM и подпись образа
        run: |
          syft $REGISTRY/playback:${{ github.sha }} -o spdx-json > sbom.json
          cosign sign --yes $REGISTRY/playback@$(crane digest $REGISTRY/playback:${{ github.sha }})
          cosign attest --yes --type spdxjson --predicate sbom.json $REGISTRY/playback@$(crane digest $REGISTRY/playback:${{ github.sha }})
      - name: Предложить обновление в GitOps-репозиторий (staging)
        run: ./tools/promote.sh playback ${{ github.sha }} staging
```

Пирамида тестирования выглядит так. Модульные тесты составляют основу и выполняются за секунды. Интеграционные тесты поднимают реальные базы в контейнерах через testcontainers, потому что моки баз данных скрывают ошибки запросов и транзакций. Контрактные тесты (Pact) проверяют, что изменение API не ломает потребителей: BFF и клиенты. Сквозные тесты в staging покрывают критичные сценарии (регистрация, оплата, старт воспроизведения с DRM) на реальных устройствах в лаборатории и выполняются перед продвижением в продакшн. Нагрузочные тесты (k6) выполняются ночью и перед крупными релизами.

## 9.7. Развёртывание и прогрессивная доставка

После успешного CI инструмент продвижения создаёт коммит в GitOps-репозиторий staging, и Argo CD разворачивает новую версию. После прохождения сквозных тестов и 30 минут стабильной работы в staging изменение автоматически продвигается в продакшн — сначала в «канареечную» ячейку каждого региона, затем волнами в остальные. Argo Rollouts управляет долей трафика через Istio и выполняет автоматический анализ, сравнивая метрики новой версии с текущей.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: playback
  namespace: playback
spec:
  replicas: 60
  revisionHistoryLimit: 5
  selector:
    matchLabels: { app: playback }
  strategy:
    canary:
      trafficRouting:
        istio:
          virtualService: { name: playback, routes: [primary] }
      steps:
        - setWeight: 1
        - pause: { duration: 5m }
        - analysis: { templates: [{ templateName: playback-canary-health }] }
        - setWeight: 10
        - pause: { duration: 10m }
        - analysis: { templates: [{ templateName: playback-canary-health }] }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100
      abortScaleDownDelaySeconds: 600
  template:
    metadata:
      labels: { app: playback }
    spec:
      nodeSelector: { node-class: playback-critical }
      tolerations: [{ key: workload, value: playback, effect: NoSchedule }]
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: playback } }
      containers:
        - name: playback
          image: registry.internal/playback@sha256:REPLACED_BY_PROMOTION
          resources:
            requests: { cpu: "2", memory: 1Gi }
            limits:   { memory: 1Gi }
          readinessProbe: { httpGet: { path: /ready, port: 8080 }, periodSeconds: 2 }
          livenessProbe:  { httpGet: { path: /live,  port: 8080 }, periodSeconds: 10 }
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: playback-canary-health
spec:
  metrics:
    - name: error-rate
      interval: 1m
      count: 5
      failureLimit: 1
      successCondition: result[0] <= 0.0005
      provider:
        prometheus:
          address: http://mimir-query.observability:8080/prometheus
          query: |
            sum(rate(playback_session_creates_total{result=~"INTERNAL|UNAVAILABLE|TIMEOUT",rollouts_pod_template_hash="{{args.canary-hash}}"}[2m]))
            / sum(rate(playback_session_creates_total{rollouts_pod_template_hash="{{args.canary-hash}}"}[2m]))
    - name: p99-latency
      interval: 1m
      count: 5
      failureLimit: 1
      successCondition: result[0] <= 0.08
      provider:
        prometheus:
          address: http://mimir-query.observability:8080/prometheus
          query: |
            histogram_quantile(0.99, sum(rate(playback_session_create_seconds{rollouts_pod_template_hash="{{args.canary-hash}}"}[2m])))
```

Изменения схем баз данных выполняются отдельно от развёртывания кода и всегда обратно совместимы по схеме «расширить — мигрировать — сузить». Сначала добавляется новый столбец или таблица (код продолжает работать со старой схемой), затем выкатывается код, который пишет в оба места, затем выполняется фоновый перенос данных, затем код переключается на чтение из нового места, и только после этого старый столбец удаляется. Миграции PostgreSQL описываются в Atlas и проверяются линтером на опасные операции (блокирующий `ALTER TABLE`, создание индекса без `CONCURRENTLY`). Для Cassandra изменения схемы применяются только аддитивно.

Флаги функций управляются через OpenFeature SDK с бэкендом Unleash, развёрнутым самостоятельно. Флаги позволяют включить функцию для внутренних сотрудников, затем для 1 % пользователей страны, затем для всех, а также мгновенно выключить функцию без развёртывания. У каждого флага есть владелец и срок жизни, а просроченные флаги автоматически становятся задачами на удаление, чтобы код не зарастал мёртвыми ветвлениями. Флаги также используются как «аварийные выключатели» для деградации дорогих функций при перегрузке.

## 9.8. Окружения

| Окружение | Назначение | Данные | Масштаб |
|-----------|------------|--------|---------|
| Локальное | Разработка одного сервиса | Фикстуры, testcontainers | Ноутбук или удалённая среда разработки |
| Эфемерное (preview) | Проверка pull request | Синтетические | Пространство имён в общем dev-кластере, живёт до слияния |
| Dev | Интеграция сервисов между командами | Синтетические | 1 регион, минимальный |
| Staging | Предрелизная проверка, сквозные тесты, устройства | Синтетические + обезличенные | 2 региона, ~5 % от продакшна |
| Load | Нагрузочные тесты | Синтетические, 50 млн аккаунтов | Одна полноразмерная ячейка по запросу |
| Production | Пользователи | Реальные | 3 региона, 10 ячеек |

## 9.9. Управление парком appliance

Собственные кэширующие appliance у провайдеров — это отдельный класс инфраструктуры: физические серверы в чужих дата-центрах без постоянного доступа инженеров. Они управляются как «скот, а не питомцы»: образ операционной системы неизменяемый и загружается по сети с проверкой подписи, конфигурация приходит из центрального управляющего сервиса, а обновления раскатываются волнами по 5 % парка с автоматической проверкой метрик отдачи. Контент на appliance заполняется ночью по манифесту, который генерирует сервис прогноза популярности. Замена вышедшего из строя сервера выполняется партнёром по стандартной процедуре: новый сервер загружается и сам подтягивает конфигурацию и контент.

## 9.10. Метрики процесса доставки

Эффективность CI/CD измеряется метриками DORA. Целевые значения: частота развёртываний — несколько раз в день на сервис, время от коммита до продакшна — меньше 1 дня (медиана около 2 часов), доля изменений, вызвавших инцидент, — меньше 5 %, время восстановления после неудачного изменения — меньше 30 минут. Эти метрики собираются автоматически из Git, Argo CD и системы инцидентов и отображаются на дашборде для каждой команды. Они используются для поиска узких мест в процессе, а не для сравнения команд между собой.

## 9.11. Альтернативы и почему не выбраны

1. **Terraform с лицензией BSL вместо OpenTofu.** Terraform — отраслевой стандарт, и HashiCorp активно его развивает. После перехода на Business Source License в 2023 году его использование в ряде сценариев стало юридически неоднозначным, а направление развития теперь определяет одна компания. OpenTofu полностью совместим по языку и провайдерам и развивается под эгидой Linux Foundation. Переход между ними в любую сторону тривиален, поэтому выбор открытой версии не несёт технических рисков.

2. **Push-развёртывание из CI (kubectl apply или helm upgrade из конвейера) вместо GitOps.** Прямое развёртывание проще для понимания и не требует отдельного контроллера. Но тогда CI получает учётные данные для записи во все продакшн-кластеры, что делает его самой ценной целью для атаки. Кроме того, при push-модели фактическое состояние кластера может разойтись с Git после ручных изменений, и это никто не заметит. GitOps устраняет обе проблемы и даёт стандартный механизм отката.

3. **Отдельные репозитории на каждый сервис (polyrepo) вместо монорепозитория.** Отдельные репозитории дают командам автономию и простые независимые конвейеры. Но при 100+ сервисах обновление общей библиотеки или генерированного кода из Protobuf превращается в сотни pull request, а версии зависимостей расходятся. Монорепозиторий с Bazel позволяет делать атомарные изменения по всем сервисам и собирать только затронутое. Клиентские приложения и ML-код при этом живут в отдельных репозиториях, потому что у них другие инструменты и циклы выпуска.

4. **Blue-green развёртывание вместо канареечного.** Blue-green (полное второе окружение с переключением трафика) даёт мгновенный откат и простую модель. Но при 60+ репликах сервиса в 10 ячейках оно требует удвоения ёмкости на время развёртывания и переключает сразу весь трафик, что делает ошибку массовой, пусть и кратковременной. Канарейка с 1 % трафика и автоматическим анализом обнаруживает проблему до того, как её увидят 99 % пользователей. Для stateful-компонентов blue-green иногда используется (например, для кластеров OpenSearch при переиндексации).

5. **Управляемые сервисы вместо самостоятельной эксплуатации Kafka, Cassandra и ClickHouse.** Amazon MSK, Amazon Keyspaces и ClickHouse Cloud снимают операционную нагрузку и хорошо подходят для небольших масштабов. При наших объёмах (сотни мегабайт в секунду в Kafka, сотни терабайт в Cassandra) наценка управляемых сервисов составляет сотни тысяч долларов в месяц, что больше стоимости выделенной команды эксплуатации. Keyspaces к тому же не полностью совместим с Cassandra. На ранних этапах дорожной карты мы используем управляемые варианты и переходим на самостоятельную эксплуатацию по мере роста.

6. **Nomad или ECS вместо Kubernetes.** HashiCorp Nomad проще Kubernetes, а Amazon ECS глубоко интегрирован с AWS и не требует управления control plane. Однако экосистема Kubernetes несравнимо богаче: операторы баз данных, Argo, Karpenter, KEDA, Istio, Kyverno — всё это стандартные инструменты, доступные «из коробки». Kubernetes также сохраняет переносимость между облаками и собственными дата-центрами. Сложность Kubernetes компенсируется платформенной командой и золотым путём.
