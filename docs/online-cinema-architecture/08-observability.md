# 8. Наблюдаемость

## 8.1. Цели наблюдаемости

Наблюдаемость — это способность ответить на любой вопрос о поведении системы в продакшне без выкатки нового кода. Для онлайн-кинотеатра это означает ответы на вопросы двух типов. Первый тип — технические: какой сервис стал медленнее, где растут ошибки, какая база перегружена. Второй тип — вопросы опыта пользователя: сколько людей прямо сейчас не могут начать просмотр, на какой CDN и у какого провайдера растёт буферизация, на какой модели ТВ падает плеер. Серверные метрики отвечают только на первый тип, поэтому наша система наблюдаемости начинается с клиента.

Стек построен на открытых стандартах: сбор выполняет OpenTelemetry (SDK в сервисах и коллекторы), метрики хранит Grafana Mimir (совместим с Prometheus), логи — Grafana Loki, трассировки — Grafana Tempo, профили — Grafana Pyroscope, а визуализация и алерты работают в Grafana. Телеметрия плееров и бизнес-события анализируются в ClickHouse. Все компоненты самостоятельно эксплуатируются в отдельных кластерах наблюдаемости в каждом регионе с глобальным слоем запросов. Это важно: система наблюдаемости не должна падать вместе с системой, которую она наблюдает.

## 8.2. Метрики

Метрики собираются по нескольким методикам, каждая из которых отвечает на свой вопрос. Ниже перечислены категории метрик и конкретные показатели в каждой.

1. **Метрики RED для каждого сервиса.** Для каждого эндпоинта и gRPC-метода собираются Rate (запросы в секунду), Errors (доля ошибок по классам: клиентские, серверные, тайм-ауты) и Duration (гистограмма задержки). Эти метрики создаются автоматически общей библиотекой middleware, поэтому ни один сервис не может их «забыть». Гистограммы используют нативный экспоненциальный формат Prometheus, который даёт точные процентили без ручного подбора корзин. По ним строятся SLO и алерты.

2. **Метрики USE для ресурсов.** Для каждого ресурса (CPU, память, диски, сеть, пулы соединений, очереди) собираются Utilization, Saturation и Errors. Насыщение особенно важно, потому что оно предсказывает проблемы раньше, чем они проявятся в задержке: например, растущая очередь ожидания соединения к базе. Метрики узлов собирает node-exporter, контейнеров — cAdvisor, а баз данных — их экспортеры. Эти метрики используются для планирования ёмкости и диагностики.

3. **Метрики качества воспроизведения (QoE).** Это главные метрики продукта, они вычисляются из телеметрии плееров: время старта (VST, video start time), доля неудачных стартов (VSF, video start failures), доля ребуферизации (время буферизации к времени просмотра), число ребуферизаций на час, средний отдаваемый битрейт, доля времени в HD и 4K, а также ошибки воспроизведения по кодам. Метрики разрезаются по CDN, edge-площадке, ASN провайдера, стране, типу устройства, версии приложения и кодеку. Именно эти разрезы позволяют найти проблему «у провайдера X на ТВ модели Y после релиза Z».

4. **Бизнес-метрики в реальном времени.** Ключевой показатель здоровья сервиса — число стартов воспроизведения в секунду (SPS, starts per second). Он имеет выраженный суточный и недельный паттерн, и отклонение от прогноза на 5–10 % надёжно указывает на проблему, даже если все технические метрики «зелёные». Кроме того, отслеживаются регистрации, входы, оформление и отмена подписок, доля успешных платежей и число активных потоков. Эти метрики видят и инженеры, и бизнес на общих дашбордах.

5. **Метрики доставки.** Для CDN и appliance собираются исходящий трафик по площадкам, доля попаданий в кэш по байтам и по запросам, TTFB сегментов, загрузка интерфейсов, ошибки 4xx и 5xx на edge и объём заполнения кэша. Метрики коммерческих CDN поступают через их API логов в реальном времени и нормализуются к общей схеме. Это позволяет сравнивать CDN между собой по одним и тем же показателям. Steering-сервис использует часть этих метрик для принятия решений.

6. **Метрики конвейеров данных.** Для Kafka собираются лаг потребителей по группам, скорость записи и чтения, а также состояние реплик. Для конвейера ингеста — длительность этапов, доля неудачных заданий кодирования, очередь ожидания и стоимость на час контента. Для CDC — задержка от фиксации транзакции до появления события в Kafka. Эти метрики показывают, насколько свежие данные видят пользователи (например, новый тайтл в поиске) и аналитики.

Пример инструментирования Go-сервиса:

```go
var (
	playbackStarts = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "playback_session_creates_total",
		Help: "Созданные сессии воспроизведения по результату",
	}, []string{"result", "device_class", "region"})

	createLatency = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:                        "playback_session_create_seconds",
		Help:                        "Задержка создания сессии воспроизведения",
		NativeHistogramBucketFactor: 1.1,
	}, []string{"region"})
)

func (h *PlaybackHandler) instrumented(ctx context.Context, req *CreateSessionRequest, u UserCtx) (*CreateSessionResponse, error) {
	ctx, span := tracer.Start(ctx, "playback.CreateSession",
		trace.WithAttributes(
			attribute.String("playable.id", req.PlayableID),
			attribute.String("device.platform", req.Device.Platform),
			attribute.Int("user.cell", u.Cell),
		))
	defer span.End()

	start := time.Now()
	resp, err := h.CreateSession(ctx, req, u)
	createLatency.WithLabelValues(h.region).Observe(time.Since(start).Seconds())

	result := "ok"
	if err != nil {
		result = errorCode(err) // STREAM_LIMIT_REACHED, SUBSCRIPTION_REQUIRED, INTERNAL ...
		span.RecordError(err)
		span.SetStatus(codes.Error, result)
	}
	playbackStarts.WithLabelValues(result, deviceClass(req.Device).String(), h.region).Inc()
	return resp, err
}
```

Кардинальность меток строго контролируется: `account_id`, `session_id`, `title_id` и другие высококардинальные значения запрещены в метках Prometheus и попадают только в трассировки, логи и ClickHouse. Это правило проверяется линтером в CI и лимитами на стороне Mimir. Нарушение кардинальности — одна из самых частых причин падения систем метрик.

## 8.3. SLO и бюджеты ошибок

| SLO | SLI (как измеряется) | Цель | Окно |
|-----|----------------------|------|------|
| Доступность старта воспроизведения | Доля успешных `POST /playback/sessions` (без клиентских ошибок) | 99,99 % | 28 дней |
| Задержка read-API | Доля запросов read-API быстрее 100 мс на шлюзе | 99 % | 28 дней |
| Время старта воспроизведения | Доля стартов с VST < 1,5 с (по телеметрии клиента) | 90 % | 28 дней |
| Качество воспроизведения | Доля сессий с rebuffer ratio < 0,5 % | 97 % | 28 дней |
| Доступность входа | Доля успешных входов и обновлений токенов | 99,99 % | 28 дней |
| Свежесть каталога | Доля изменений, видимых в API в течение 60 с | 99 % | 28 дней |
| TTFB сегментов | Доля сегментов с TTFB < 100 мс на edge | 95 % | 28 дней |

SLO описаны как код в формате OpenSLO и генерируют правила записи и алерты автоматически (через Sloth). Бюджет ошибок используется как инструмент управления: если сервис израсходовал больше 50 % месячного бюджета, релизы новых функций в нём замораживаются до стабилизации, а работа над надёжностью получает приоритет. Это договорённость между продуктом и инженерией, а не решение одной стороны.

## 8.4. Логи

Логи пишутся в структурированном формате JSON с обязательными полями: `ts`, `level`, `service`, `version`, `region`, `cell`, `trace_id`, `span_id`, `msg`. Благодаря `trace_id` из любой строки лога можно перейти к полной трассировке запроса. Персональные данные в логах запрещены: вместо e-mail пишется хеш, IP-адрес усекается до подсети, а общая библиотека логирования маскирует поля по списку имён и регулярным выражениям. Проверки в CI ищут вызовы логирования, в которые передаются объекты с персональными данными.

Объём логов при нашей нагрузке огромен, поэтому действует дисциплина уровней и сэмплирования. На уровне INFO каждый запрос не логируется: для этого есть метрики и трассировки. Логируются события жизненного цикла, ошибки и предупреждения. Ошибки логируются всегда, но повторяющиеся одинаковые ошибки агрегируются (одна запись с счётчиком за 10 секунд). Журналы доступа шлюза пишутся полностью, но хранятся в дешёвом объектном хранилище и запрашиваются через Loki только по необходимости.

| Тип логов | Хранение «горячее» | Хранение архивное | Объём в сутки |
|-----------|--------------------|-------------------|---------------|
| Логи приложений | 14 дней (Loki) | 90 дней (S3) | ~8 ТБ |
| Журналы доступа шлюза и edge | 7 дней | 90 дней | ~25 ТБ |
| Логи аудита и безопасности | 90 дней (SIEM) | 7 лет (S3 Object Lock) | ~200 ГБ |
| Логи CDN | 3 дня | 30 дней | ~40 ТБ |

```python
# Структурированное логирование в Python-сервисах с автоматической маскировкой PII.
import logging, re, structlog
from opentelemetry import trace

EMAIL = re.compile(r"[^@\s]+@[^@\s]+")
SENSITIVE_KEYS = {"email", "password", "token", "refresh_token", "card", "phone", "ip"}

def redact(_, __, event_dict):
    for k in list(event_dict):
        if k in SENSITIVE_KEYS:
            event_dict[k] = "[REDACTED]"
        elif isinstance(event_dict[k], str):
            event_dict[k] = EMAIL.sub("[EMAIL]", event_dict[k])
    return event_dict

def add_trace(_, __, event_dict):
    ctx = trace.get_current_span().get_span_context()
    if ctx.is_valid:
        event_dict["trace_id"] = format(ctx.trace_id, "032x")
        event_dict["span_id"] = format(ctx.span_id, "016x")
    return event_dict

structlog.configure(processors=[
    structlog.contextvars.merge_contextvars,
    structlog.processors.add_log_level,
    structlog.processors.TimeStamper(fmt="iso", utc=True),
    add_trace,
    redact,
    structlog.processors.JSONRenderer(),
])
log = structlog.get_logger(service="ingest-worker", region="eu-central-1")
log.info("encode_chunk_done", asset_id="0192...", chunk=17, codec="av01", seconds=412.5)
```

## 8.5. Распределённая трассировка

Каждый запрос получает трассировку, которая проходит через edge, шлюз, BFF, доменные сервисы, кэши и базы данных. Контекст распространяется по стандарту W3C Trace Context через HTTP-заголовки, метаданные gRPC и заголовки сообщений Kafka. Это позволяет увидеть и асинхронную часть: как событие «подписка оформлена» прошло через Kafka к сервису уведомлений. Трассировки — главный инструмент поиска причины, когда метрики показывают только сам факт деградации.

При 300 тысячах RPS хранить все трассировки невозможно и бессмысленно, поэтому используется двухуровневое сэмплирование. На стороне сервисов сохраняются все спаны (head sampling = 100 %), но коллекторы OpenTelemetry выполняют хвостовое сэмплирование (tail sampling) после завершения трассировки. Сохраняются 100 % трассировок с ошибками, 100 % трассировок медленнее p99 для своего эндпоинта, 100 % трассировок с флагом отладки (его можно включить для конкретного аккаунта при обращении в поддержку) и 1 % остальных. Итоговый объём — около 3 % от всех трассировок, но в него попадают почти все интересные.

```yaml
# Хвостовое сэмплирование в OpenTelemetry Collector.
processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 2000000
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-playback
        type: and
        and:
          and_sub_policy:
            - name: playback-service
              type: string_attribute
              string_attribute: { key: service.name, values: [playback, drm-license] }
            - name: slower-than-80ms
              type: latency
              latency: { threshold_ms: 80 }
      - name: slow-any
        type: latency
        latency: { threshold_ms: 250 }
      - name: debug-flag
        type: string_attribute
        string_attribute: { key: debug.trace, values: ["true"] }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }
```

Трассировки связаны с метриками через экземпляры (exemplars): на графике задержки можно нажать на точку всплеска и открыть конкретную медленную трассировку. Трассировки также связаны с профилями CPU (Pyroscope), поэтому для медленного спана видно, какие функции потребляли процессор. Этот переход от «метрика выросла» к «вот строка кода» занимает минуты, а не часы.

## 8.6. Телеметрия клиентов и RUM

Клиентская телеметрия — единственный источник правды о реальном опыте пользователя, потому что многие проблемы (плохой Wi-Fi, проблемы конкретного провайдера, ошибки декодера на модели ТВ) серверу не видны. Плееры отправляют пакеты событий раз в 30 секунд и немедленно при ошибках: старт, переключения битрейта, ребуферизации, смены CDN, ошибки с кодами, остановки. Приложения также отправляют метрики производительности интерфейса: время загрузки главной, задержку отклика на пульт, падения приложения. Схема событий версионирована и валидируется при приёме.

## 8.7. Алертинг

Алерты делятся на два класса. Страница (page) будит дежурного и допустима только для проблем, которые прямо сейчас влияют на пользователей и требуют действия человека. Тикет (ticket) создаёт задачу для рабочего времени. Основной тип алерта — сжигание бюджета ошибок SLO в нескольких окнах (multi-window, multi-burn-rate): он срабатывает быстро при сильной деградации и не шумит при кратковременных всплесках. Алерты по причинам (CPU высокий, диск заполняется) допускаются только как тикеты либо как страницы для неизбежных проблем, например диска, который заполнится в ближайший час.

```yaml
# Алерты по бюджету ошибок SLO старта воспроизведения (99,99 %).
groups:
  - name: slo-playback-start
    rules:
      - record: slo:playback_start_errors:ratio_rate5m
        expr: |
          sum(rate(playback_session_creates_total{result=~"INTERNAL|UNAVAILABLE|TIMEOUT"}[5m]))
          / sum(rate(playback_session_creates_total[5m]))
      - record: slo:playback_start_errors:ratio_rate1h
        expr: |
          sum(rate(playback_session_creates_total{result=~"INTERNAL|UNAVAILABLE|TIMEOUT"}[1h]))
          / sum(rate(playback_session_creates_total[1h]))
      - record: slo:playback_start_errors:ratio_rate6h
        expr: |
          sum(rate(playback_session_creates_total{result=~"INTERNAL|UNAVAILABLE|TIMEOUT"}[6h]))
          / sum(rate(playback_session_creates_total[6h]))
      - record: slo:playback_start_errors:ratio_rate30m
        expr: |
          sum(rate(playback_session_creates_total{result=~"INTERNAL|UNAVAILABLE|TIMEOUT"}[30m]))
          / sum(rate(playback_session_creates_total[30m]))
      # Быстрое сжигание: 2 % месячного бюджета за 1 час (burn rate 14.4).
      - alert: PlaybackStartSLOFastBurn
        expr: |
          slo:playback_start_errors:ratio_rate1h > (14.4 * 0.0001)
          and slo:playback_start_errors:ratio_rate5m > (14.4 * 0.0001)
        labels: { severity: page, team: playback }
        annotations:
          summary: "Быстрое сжигание бюджета SLO старта воспроизведения"
          runbook: "https://runbooks.internal/playback/start-slo"
          dashboard: "https://grafana.internal/d/playback-start"
      # Медленное сжигание: 5 % бюджета за 6 часов (burn rate 6).
      - alert: PlaybackStartSLOSlowBurn
        expr: |
          slo:playback_start_errors:ratio_rate6h > (6 * 0.0001)
          and slo:playback_start_errors:ratio_rate30m > (6 * 0.0001)
        labels: { severity: page, team: playback }
      # Бизнес-сигнал: SPS ниже прогноза на 10 % в течение 5 минут.
      - alert: StartsPerSecondAnomaly
        expr: |
          sum(rate(playback_session_creates_total{result="ok"}[2m]))
          < 0.9 * sps:forecast:rate2m
        for: 5m
        labels: { severity: page, team: incident-command }
```

Каждый алерт обязан иметь ссылку на runbook с конкретными шагами диагностики и смягчения, а также ссылку на дашборд. Алерт без runbook не проходит ревью. Раз в месяц команды разбирают статистику своих алертов: алерт, который срабатывал без необходимости действий, настраивается или удаляется. Цель — не больше двух страниц за смену дежурного в среднем.

## 8.8. Дашборды и инцидент-менеджмент

Дашборды организованы иерархически. Верхний уровень — «здоровье сервиса»: SPS против прогноза, доступность старта, VST, ребуферизация, трафик CDN и статус регионов. Этот дашборд показан на экранах в центре мониторинга. Следующий уровень — дашборды доменов (воспроизведение, доставка, коммерция), а нижний — дашборды отдельных сервисов, сгенерированные из шаблона. Дашборды описаны как код (Grafonnet/Jsonnet) и хранятся в Git.

Инциденты обрабатываются по единому процессу. Дежурный по сервису подтверждает страницу за 5 минут. При влиянии на пользователей назначается инцидент-менеджер, открывается канал инцидента и страница статуса. Приоритет — смягчение (откат, переключение трафика, отключение флага функции), а не поиск первопричины. После каждого инцидента уровня SEV1 и SEV2 в течение 5 рабочих дней проводится разбор без поиска виноватых, с задачами по предотвращению повторения и сроками их выполнения.

Синтетический мониторинг дополняет реальные данные. Роботы из 30 точек мира каждую минуту выполняют сценарии: вход, открытие главной, поиск, старт воспроизведения тестового тайтла с реальной DRM-лицензией и загрузкой сегментов с каждой CDN. Синтетика обнаруживает проблемы в часы низкого трафика, когда статистики реальных пользователей недостаточно, и проверяет пути, которые пользователи проходят редко. Результаты синтетики участвуют в SLO как отдельный сигнал.

```sql
-- ClickHouse: топ-10 комбинаций «CDN × провайдер × устройство» с худшим временем старта за 15 минут.
SELECT cdn, isp_asn, device_type,
       quantileMerge(0.9)(startup_p90_state) AS vst_p90_ms,
       sum(starts) AS starts,
       sum(errors) / sum(starts) AS start_failure_rate
FROM qoe.playback_minute
WHERE ts >= now() - INTERVAL 15 MINUTE
GROUP BY cdn, isp_asn, device_type
HAVING starts > 200
ORDER BY vst_p90_ms DESC
LIMIT 10;
```

## 8.9. Альтернативы и почему не выбраны

1. **Коммерческая SaaS-платформа наблюдаемости (Datadog, New Relic, Dynatrace).** SaaS-платформы дают отличный пользовательский опыт, быструю настройку и не требуют эксплуатации, и на старте проекта это разумный выбор. Но их ценообразование зависит от числа узлов, объёма логов и количества пользовательских метрик, и при нашем масштабе (тысячи узлов, десятки терабайт логов в сутки) годовой счёт исчисляется десятками миллионов долларов. Кроме того, отправка всех логов внешнему провайдеру усложняет соответствие требованиям о персональных данных. Самостоятельно эксплуатируемый стек Grafana обходится в 5–10 раз дешевле при сопоставимых возможностях.

2. **Стек ELK (Elasticsearch, Logstash, Kibana) для логов.** ELK — классическое и мощное решение с полнотекстовым поиском по логам. Однако полнотекстовое индексирование каждого поля при 30+ ТБ логов в сутки требует огромного кластера с дорогим хранилищем. Loki индексирует только метки, а содержимое хранит в сжатом виде в объектном хранилище, что снижает стоимость хранения в 10 и более раз. Поиск по содержимому в Loki медленнее, но при наличии `trace_id` и меток он редко нужен.

3. **Prometheus без долгосрочного хранилища.** Отдельные серверы Prometheus в каждом кластере проще в развёртывании, но у них нет глобального представления, высокой доступности и долгого хранения. При десятках кластеров в трёх регионах запросы «по всей системе» становятся невозможными. Mimir даёт горизонтально масштабируемое хранилище, совместимое с PromQL, с хранением данных в S3 и глобальными запросами. Thanos был бы равноценной альтернативой, а Mimir выбран за лучшую производительность на запись при наших объёмах.

4. **Head sampling (сэмплирование в начале запроса) вместо хвостового.** Решение о сохранении трассировки в начале запроса проще и дешевле: коллекторам не нужно держать спаны в памяти. Но при 1 % head sampling мы теряем 99 % трассировок с ошибками и медленных запросов, то есть именно те, что нужны для диагностики. Хвостовое сэмплирование требует больше памяти в коллекторах (гигабайты на коллектор), но сохраняет все значимые трассировки. Эта цена оправдана.

5. **Алерты по порогам технических метрик вместо SLO.** Алерты вида «CPU больше 80 %» или «ошибок больше 100 в минуту» интуитивны и быстро настраиваются. Но они шумят (высокий CPU часто не влияет на пользователей) и одновременно пропускают реальные проблемы (медленная деградация задержки без всплесков). Алерты по сжиганию бюджета SLO напрямую связаны с опытом пользователя и масштабируются с трафиком. Технические пороги остаются только как тикеты для превентивной работы.

6. **Хранение телеметрии плееров в системе метрик Prometheus.** Можно было бы экспортировать QoE как метрики Prometheus и строить все дашборды в одном месте. Однако QoE требует разрезов по высококардинальным измерениям (ASN провайдера — десятки тысяч значений, модели устройств — тысячи, версии приложений — сотни), и их произведение взорвало бы кардинальность Prometheus. ClickHouse создан для таких аналитических запросов по сырым событиям. В Prometheus мы экспортируем только агрегаты верхнего уровня для алертов.
