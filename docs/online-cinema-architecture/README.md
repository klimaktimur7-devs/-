# Архитектура распределённой платформы онлайн-кинотеатра

Этот каталог содержит полный проектный документ распределённой системы онлайн-кинотеатра, спроектированной «с чистого листа». Система рассчитана на 50 миллионов активных пользователей в месяц, каталог объёмом 10 петабайт видео, глобальную доставку через многоуровневую CDN и задержку пользовательских операций менее 100 мс. Документ разбит на 12 разделов и глоссарий. Каждый раздел самодостаточен, но все цифры в документе выводятся из одной модели нагрузки, описанной ниже, поэтому разделы согласованы между собой.

## Базовая модель нагрузки (единая для всех разделов)

Все расчёты ёмкости, стоимости и рисков в документе опираются на одни и те же допущения. Если реальные значения окажутся другими, достаточно пересчитать эту таблицу: остальные разделы масштабируются от неё линейно или почти линейно. Значения выбраны консервативно, с учётом публичных отраслевых данных о поведении зрителей стриминговых сервисов.

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Активные пользователи в месяц (MAU) | 50 000 000 | Условие задачи |
| Активные пользователи в день (DAU) | 18 000 000 | 36 % от MAU, типично для SVOD |
| Среднее время просмотра на DAU | 1,2 часа в день | Смесь мобильных и ТВ-сессий |
| Средний отдаваемый битрейт | 3,5 Мбит/с | Адаптивный битрейт, смесь SD/HD/4K |
| Одновременные потоки в пике | 4 000 000 | ~22 % DAU в вечерний пиковый час |
| Пиковый исходящий трафик | 14 Тбит/с | Проектный запас до 20 Тбит/с |
| Месячный объём трафика | ≈ 1,0 ЭБ (1 020 ПБ) | 648 млн часов × 1,575 ГБ/ч |
| Объём хранилища видео | 10 ПБ | 4 ПБ мастер-копий, 5,5 ПБ рендишенов, 0,5 ПБ прочего |
| Объём контента | ≈ 100 000 часов | 25 000 тайтлов, 150 000 воспроизводимых единиц |
| Пиковый RPS API (без сегментов) | ≈ 300 000 | Включая heartbeat и телеметрию |
| Пиковый RPS к CDN (сегменты) | ≈ 2 000 000 | Сегменты по 4 секунды, видео + аудио |
| Регионы облака | 3 активных | us-east-1, eu-central-1, ap-southeast-1 |

## Целевые SLO

Требование «latency < 100 мс» в документе трактуется точно и измеримо, потому что для видеосервиса одна цифра задержки может означать очень разные вещи. Мы разделяем задержку API, задержку доставки видеосегмента и время старта воспроизведения, а затем задаём для каждой из них отдельную цель. Время старта воспроизведения (от нажатия «Смотреть» до первого кадра) физически не укладывается в 100 мс: оно включает DRM-лицензию, загрузку манифеста и первого сегмента, а также инициализацию декодера. Поэтому для него задана отдельная, отраслево реалистичная цель.

| Показатель | Цель |
|------------|------|
| Задержка read-API (p99, измеряется на edge-шлюзе) | < 100 мс |
| Задержка read-API (p50) | < 30 мс |
| Задержка write-API (p99) | < 150 мс |
| TTFB видеосегмента с edge-кэша (p95) | < 100 мс |
| Доля попаданий в кэш CDN по байтам | ≥ 97 % |
| Время старта воспроизведения (p90) | < 1,5 с |
| Доля буферизации (rebuffer ratio) | < 0,5 % времени просмотра |
| Доступность старта воспроизведения | 99,99 % в месяц |
| Доступность остальных пользовательских функций | 99,95 % в месяц |

## Как читать документ

Разделы 1–4 описывают, из чего состоит система: компоненты, технологии, данные и интерфейсы. Разделы 5–9 объясняют, как система переносит нагрузку и отказы, как защищается, как её наблюдают и как доставляют изменения. Разделы 10–12 посвящены деньгам, рискам и плану внедрения. В конце каждого раздела есть подраздел «Альтернативы и почему не выбраны», где перечислены отвергнутые варианты с обоснованием. Глоссарий в конце раскрывает 50 ключевых терминов.
